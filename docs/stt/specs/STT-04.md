# STT-04 · 识别语言判定不再自锁

## 架构与接口依据

本 SPEC 必须实现 [模块架构与接口](../ARCHITECTURE.md) 中对应阶段的端口、事件、状态与错误语义；通过 adapter 兼容现有实现。下方 AC 同时验证这些契约，无需启动其他真实模块。

需求与边界见 [模块 PRD](../PRD.md)，依赖遵循 [共享契约](../../modules/CONTRACTS.md)。

修掉 Web Speech 退路上「说日语被识别成中文，且再也回不来」的自锁闭环；顺带修同一根因造成的 TTS 选错音色。不动 `detectLanguage` 的文本分类语义。

## 现象与根因（已查证）

用户报告：说日语，识别出来是中文。

链条（`App.tsx:55` → `preferredRecognitionLanguage` → `detectLanguage` → `webSpeechInput.recognition.lang`）：

1. `detectLanguage` 的规则是「有假名算日语，**无假名有汉字算中文**」——这条写在 `domain/language.test.ts:9`，是明确决策，对中文没错。
2. 但日语短句经常没有假名。用生产函数实测：

   ```
   大丈夫 → zh   元気 → zh   一緒 → zh   本当 → zh
   今日 → zh     明日 → zh   最近 → zh   全部 → zh
   写真 → zh     時間 → zh   電話 → zh   仕事 → zh
   先生 → zh     学校 → zh
   何も変わりません → ja   こんばんは → ja   今日は忙しかった → ja
   ```

3. 判成 zh 之后，下一段 `recognition.lang = "zh-CN"`。Web Speech 用中文听日语，**吐出来的一定是纯汉字、一定没有假名**。
4. 第 3 步的输出又进入第 1 步 → 判成 zh → 回到第 2 步。

**这是一个单向闩**：想靠说日语翻回 `ja-JP`，需要识别结果里出现假名；而中文引擎永远不产生假名。唯一出口是手打一句带假名的日文。用户感受到的「有时候」不是随机，是掉进去之后就一直是。

触发它不需要说出没有假名的日语——`resolveLanguage` 取的是最近 4 条**用户消息**，不区分来源，所以**用键盘打一句中文，下一段语音就按中文识别**。

前提条件：本机 `http://127.0.0.1:8080` 的 whisper-server 没有运行（已实测连不上），`voice.backend` 在桌面库里没有存值即默认 `auto`，于是每次语音都走 Web Speech 退路。走 whisper 时 `language: "auto"`，整个问题不存在。

## 取舍

**为什么不是「让用户自己选语言」**：PRD 明确要求不需要用户参与，这一条不推翻。

**为什么不能简单地把「无假名纯汉字」判成日语**：那会让中文用户每句话都被日语引擎听，只是把受害者换了个人。

**所以改判定的方向是「证据」而不是「分类」**：只在拿到确凿证据时切换识别语言，拿不到证据就保持上一次用过的语言，而不是强行选一个。这一点与本次调查初期给出的口头建议不同——初期说「不建议靠字形区分日本汉字和简体字」，那是针对「用字形做兜底分类」；用字形做**确凿证据**是另一回事，因为它只负责「确定是」，不负责「那就只能是」，判不出时不产生任何切换。

**为什么 `detectLanguage` 不动**：它还有文本分类的用途，那 5 条现有测试是对的。新判定是并列的第二个函数，不是替换。

## 实现时发现的前提修正

本 SPEC 初稿隐含一个错误前提：「把判定修好就能解开自锁」。不成立。

要从 `zh-CN` 回到 `ja-JP`，需要一条「这是日语」的证据；而在 `zh-CN` 上的唯一文本来源就是中文引擎本身，**它既不会吐出假名，也不会吐出日语字形**。单语言引擎加纯文本信号，信息上就不可能自己纠正——这不是判定写得好不好的问题。

所以本 SPEC 实际交付的是：**把误入 `zh-CN` 的概率降下来**（两条最常见的路径：没有假名的日语、打字的中文，都不再触发切换）。已经锁进去的状态靠本 SPEC 解不开。

因此**逃生阀从「可选后续」升为必须**，已由 [FE-13](../../frontend/specs/FE-13.md) 交付：语音页显示当前按哪个语言识别，点一下能改。用户随后实测到的是 `en-US` 方向的同一个闩（「こんにちは」被英文引擎转成 `konichiwa`），三个方向至此都见过。根治仍然是本地 whisper（`language: "auto"`）。

## 追加：探活别挡住开始听（AC-G）

用户报「点实时语音会卡一会然后不识别」。在浏览器里实测：

```
fetch("http://127.0.0.1:8080/")   →  2023ms / 255ms / 1766ms（全部 Failed to fetch）
navigator.mediaDevices.getUserMedia  →  34ms
```

`auto` 模式每次进语音页都要先探一次本地 whisper，而它**串行挡在启动识别之前**。`probe()` 里写的 `connectTimeout: 2000` 只有 `@tauri-apps/plugin-http` 认，**浏览器的 fetch 把它当不存在的字段直接忽略**——那 2 秒是 Windows 自己的连接重试，代码根本没在管。用户点完就说话，那段时间里说的话没人听，正是「然后不识别」。

改法是给它一个两边都认的超时（`signal: AbortSignal.timeout(800)`，本地回环上服务活着只需几毫秒，等过 800ms 就可以当它没开）。

## 不在本 SPEC

- **混说识别**（一句话里中日英混）：那是 whisper 的能力，本 SPEC 只让退路不出错，不假装退路能混说。
- **语音页露出当前识别语言、并允许手动切一次**：这是逃生阀，属前端，另开 FE SPEC。本 SPEC 只保证 `ResolvedInputEngine` 把语言与降级如实带出来供 UI 使用。
- 字形的全量分类表。证据表是白名单，只收「确定是」的字，漏判即无证据，不追求覆盖。
- 真实麦克风与真人发音验收：仍按 [STT-03](STT-03.md) 的 DEFERRED 状态，不自动恢复。

只执行当前 SPEC 的本模块测试；其他模块使用 fake/mock。验收报告放 `../reports/STT-04_ACCEPTANCE.md`。全流程测试仅在必须联调或大任务完成时按 [集成 SPEC](../../integration/SPEC.md) 执行；真人设备后置项不自动恢复。
