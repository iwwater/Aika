## 先回答规划文档 §7 问题 3：只读

**控制台只读，写操作只走应用内接口。** 理由不是「安全起见」这种套话，而是三条具体的：

1. **写进去的数据没人对得上账。** 记忆有抑制标记与 supersede 关系、消息有摘要覆盖范围、trace 有自己的表。手写一条 `UPDATE` 不会触发任何联动，库里从此是一份「代码认不出来的状态」，之后每一个 bug 都要先怀疑是不是那次手改。
2. **删除在这个应用里是有语义的。** `forget()` 会落抑制标记、让摘要作废；`DELETE FROM memories` 只是让那一行消失，被删的记忆下一轮抽取又会回来——用户会认为「删不掉」。
3. **调试价值几乎全在读。** 「她为什么记得这个」「这条消息到底存进去没有」都是 SELECT 能回答的。为了偶尔想改一行而留一个能毁掉整库的入口，不划算。

代价说清楚：真要改数据得自己开 DB Browser，或者走应用内的记忆管理页（FE-11）。这是刻意的。

## 交付

规划文档的 F8，工作台新增一个「存储」页签：

- **分表浏览**：表与视图清单（含行数），点进去看前 N 行；
- **schema 查看**：列名、类型、非空、主键，以及建表 SQL 原文；
- **只读 SQL 控制台**：自己写 SELECT，结果以表格显示。

## 边界

- **不做写入**（见上）。不做导出 CSV、不做编辑单元格、不做分页跳转（只给前 N 行与总行数）。
- 不碰存储契约：`sqlExecutor` 已经是可选成员，本 SPEC 一个端口都不加。
- 浏览器降级（localStorage）没有 `sqlExecutor`：页面**说清楚这台机器上没有 SQL 能力**，不给一张空表格假装库是空的。
- 门禁是**文本判定**，不是数据库层面的只读连接——`plugin-sql` 只给一个执行器，没有只读连接可用。这一点必须在页面上如实写出来，不能让人以为有数据库级保证。

## 只读门禁的设计

判定必须**跳过字符串字面量与注释**再找关键字，否则两头都错：

- 漏判：`SELECT 1; DROP TABLE memories` —— 只看开头以为是 SELECT；
- 误杀：`SELECT * FROM messages WHERE content LIKE '%delete%'` —— 只看关键字就把正常查询拦了。

所以写一个最小 tokenizer：识别 `'...'`（含 `''` 转义）、`"..."`、`` `...` ``、`[...]`、`--` 与 `/* */`，剥掉之后再判。规则：

1. 剥注释后只能有**一条**语句（尾部分号允许）；
2. 首个关键字必须是 `SELECT` / `WITH` / `EXPLAIN` / `PRAGMA`；
3. `PRAGMA` 只允许白名单里的只读项（`table_info` / `table_list` / `index_list` / `index_info` / `foreign_key_list` / `database_list`），且不许带 `=`（`PRAGMA journal_mode=WAL` 是写）；
4. 语句体内（字符串与注释之外）出现任何写关键字一律拒绝：`INSERT` / `UPDATE` / `DELETE` / `DROP` / `ALTER` / `CREATE` / `REPLACE` / `TRUNCATE` / `ATTACH` / `DETACH` / `VACUUM` / `REINDEX` / `BEGIN` / `COMMIT` / `ROLLBACK` / `SAVEPOINT` / `RELEASE` / `GRANT`。CTE 后面接写（`WITH x AS (…) DELETE FROM …`）因此也被拦下。

拒绝时给**具体原因**，不是一句「非法语句」——「你写了 DELETE」和「你写了两条语句」要分得开，否则用户只能瞎猜。
