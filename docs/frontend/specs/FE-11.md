## 交付

规划文档的 F7：把右栏那份 12 条上限的记忆列表升级为整页——**按 V2 的原貌管理**，而不是继续看降级过的 V1 视图。

右栏现在显示的是 `toLegacyMemoryRecord()` 的结果：type 被压成 5 个旧 category、`candidate/superseded` 被压成 `pending`、来源与置信度整个丢掉。管理一条记忆需要知道的恰恰是被压掉的那些：**这句话从哪来、还能不能当真、是不是已经被新的取代了**。

- 按 type 筛选、按状态筛选、文本搜索；
- pending（`candidate`）审核流：待过目的排在前面，可单条确认、可批量确认；
- 编辑正文与类型；
- 批量确认 / 批量删除；
- 来源标注：`messages`（几条来源消息）、`legacy`（迁移来的，**来源不明**）、`userEdit`（你手写的）。

## 边界

- **不改存储与检索算法**。`MemoryRepository` 的 `list/upsert/supersede/forget` 原样使用，不新增查询能力，不动 `rankMemories`。
- 不做记忆的手动新增（「凭空加一条她该记得的事」是另一件事，会绕开抽取与来源溯源）。
- 不做导入导出、不做按时间范围清理。
- 不碰右栏那份列表本身的布局——它继续存在，只是删改之后要跟着变（见 AC-F）。
- 批量删除**不是事务**：仓储只有逐条 `forget`。因此删一半失败必须如实报告，不允许显示成全部成功。

## 契约追加（v1 之后）

`MemoryAccess` 增加一对变更通知：

```ts
/** 记忆内容变了（确认、编辑、删除都算）。删除时先触发 onInvalidate，再触发这个。 */
onChanged(listener: () => void): () => void;
/** 管理界面改完之后调用，通知其它消费者重读。仓储自己不知道界面存在。 */
notifyChanged(): void;
```

为什么必须加：仓储只在 `forget` 时有回调（`onInvalidate`，语义是「摘要作废」），确认与编辑一声不吭。没有这个通知，在管理页删掉一条记忆之后，右栏还挂着它——同一份数据两个界面各说各话，比不做这个页面更糟。

受影响消费者：`memoryPlugin`（扇出）、`companionPresenter`（订阅后重读列表）、新的 `memoryPresenter`（改完调用）。`onInvalidate` 的既有语义与调用时机不变。
