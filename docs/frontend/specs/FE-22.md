## 架构与接口依据

本 SPEC 必须实现 [模块架构与接口](../ARCHITECTURE.md) 中对应阶段的端口、事件、状态与错误语义；通过 adapter 兼容现有实现。下方 AC 同时验证这些契约，无需启动其他真实模块。

需求与边界见 [模块 PRD](../PRD.md)「事件与主动策略」，依赖遵循 [共享契约](../../modules/CONTRACTS.md)。端口契约见 [FE-18](FE-18.md)。

现状：已有**时间驱动**的主动消息——`domain/proactive.ts` 的 `canSend`（quiet hours、`MAX_DAILY_MESSAGES = 6`、`MIN_INTERVAL_MS = 90min`）+ `chooseProactiveReason`，presenter 的 `runProactiveTick` 经 `sendTurn(…, "proactive")` 发送；`TurnSource` 早已含 `"proactive"`，主动轮不 persist 成用户消息，`providerAdapter` 已区分。本 SPEC 把环境事件接成**事件驱动的第二触发源**，进同一套闸门——不建第二套主动路径。

## 设计

- 接线：companionPresenter 订阅 monitor（FE-18 去重/频控复用）→ `ProactivePolicy.evaluate`（该端口第一次有生产调用方）→ trigger → 走与 `runProactiveTick` **完全相同**的发送路径：`canSend` 终审 → `sendTurn(…, "proactive")` → `proactiveLastSentAt` / `proactiveLastReason` 落键 → `Notifier.notify`。
- 规则实现：`src/services/environment/ruleProactivePolicy.ts` 替换 FE-18 的静态 fake。规则：`game_event`（victory/defeat）强信号直接候选 trigger；`foreground_changed` / `screen_keyword` 弱信号需持续时长 + 累计次数门槛；`userBusy`（由可信观测提供true/false/unknown，不能仅凭进程名判全屏）时非游戏事件一律 ignore。
- `domain/proactive.ts` 可选追加：`ProactiveGateInput.environmentBusy?: boolean`；`chooseProactiveReason` 输入追加 `environment?`（环形缓冲摘要），`ProactiveReasonKind` 新增成员（`game_result` / `long_session` 等，穷举处补分支）。
- **remember 的语义**：事件进入内存环形缓冲（上限 20 条），供下一次 reason 选择与 FE-19 contextSource 摘要引用；**不写长期记忆表**。
- 设置：`SETTING_KEYS.environmentProactiveEnabled`（默认 `"false"`——传感器开着也不主动搭话，直到这里也打开）；设置区文案写明「传感器开关」与「允许主动搭话」是两层。

## 取舍

**policy 与 `canSend` 双层保留**：policy 判「这个事件值不值得说」（事件维度），`canSend` 判「现在能不能说」（时间/额度维度）。合成一层会让 policy 失去纯函数输入，conformance 无从谈起；两层各司其职，trigger 仍被闸门终审。

**复用 tick 的发送函数，不是平行实现**：两条触发源、一条发送路径——主动消息的可观测性（lastReason、每日计数、UI「主动」标签、系统通知）自动一致，不会出现环境触发的消息绕过频控或漏记。

**remember 不写长期记忆**：把传感器文本自动写成记忆，是隐私与质量的双重风险（OCR 误读会固化为「事实」）。环形缓冲是易失的弱信号池，本期只进入易失环形缓冲；即使LLM返回候选也不能绕过RT-04来源校验变成User Soul。

## 可测策略输入

弱信号默认要求sustainedMs≥30000且occurrencesInWindow≥2（窗口60s）；聚合器只保存有界事件摘要，纯policy不得隐藏计数器。game_event也需confidence≥0.8及全局canSend终审，unknown忙碌状态默认忽略。值以配置常量冻结，改变需同步fixture与记录理由，不按验收结果临时放宽。

这些阈值只是本版规则，不承诺事件识别准确率。新增生产policy测试覆盖临界值和相同输入确定性；发送预约与计数提交失败明确恢复，不能留永远busy或同刻多发。
