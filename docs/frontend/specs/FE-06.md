# FE-06 · 撤回与重新生成

## 架构与接口依据

本 SPEC 必须实现 [模块架构与接口](../ARCHITECTURE.md) 中对应阶段的端口、事件、状态与错误语义；通过 adapter 兼容现有实现。下方 AC 同时验证这些契约，无需启动其他真实模块。

需求与边界见 [模块 PRD](../PRD.md)，依赖遵循 [共享契约](../../modules/CONTRACTS.md)。

前置：[CORE-08](../../core/specs/CORE-08_MESSAGE_DELETION.md)（`deleteMessages`）、[FE-05](FE-05.md)（轮次归组与「先删再投」）已通过。

## 交付

[规划文档](../../PLAN_DEV_DEBUG_WORKBENCH.md) F1 里剩下的两项消息级操作：

- **撤回**：删掉这一轮，并连带遗忘由它喂出来的**未确认**记忆候选。
- **重新生成**：对已经成功的那一轮换一个回复——机制与 FE-05 的重试相同（先整轮删掉，再用同一句原话重投），区别只在入口出现在成功的气泡上。

三个入口（重试 / 重新生成 / 撤回）合并成一排气泡操作，FE-05 的单按钮组件 `MessageRetry` 由 `MessageActions` 取代；判定仍全部在 domain。

## §7 问题 4 的回答（撤回是否连带撤记忆）

规划文档 §7 建议「是，撤回=该轮从未发生」。本 SPEC **采纳但收窄**，理由是查证出来的两件事：

1. `MemoryRecordV2.sourceMessageIds` 确实存在，`runBackgroundMemoryWork` 落候选时写了它（注释原话：「也是删除联动的依据」），所以溯源可行。
2. 但抽取输入是**最近 4 条消息**，一条记忆的来源常常跨两轮。「来源与被撤回消息有交集」因此是个宽判据，拿它无差别删除会牵连别的轮次。

所以规则是：来源与被撤回消息有交集、且状态仍为 `candidate` 的记忆，走 `repository.forget()`（落抑制标记，来源不会让它复活）；**状态为 `confirmed` 的一律保留**——那是用户明确说过要留的，不能因为一次撤回悄悄消失。V1 记忆路径没有来源字段，无法溯源，撤回只删消息、不动记忆，如实写进报告而不是假装联动了。

## 边界

- 不做：Rewind（按时间截断 + 摘要 gap 标注）、点击发音、用户消息编辑。
- 不改 `CompanionRuntime` 与存储契约；重新生成走普通 `submit()`。
- 不动摘要：撤回不触发摘要重压缩（`forget()` 自带的失效事件除外，那是既有行为）。
- 开场白（`welcome`）不可撤回：它从来不落库，删它只是让问候语在本次会话里凭空消失。
