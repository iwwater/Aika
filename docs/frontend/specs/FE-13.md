# FE-13 · 语音页露出识别语言并允许改掉

## 架构与接口依据

本 SPEC 必须实现 [模块架构与接口](../ARCHITECTURE.md) 中对应阶段的端口、事件、状态与错误语义；通过 adapter 兼容现有实现。下方 AC 同时验证这些契约，无需启动其他真实模块。

需求与边界见 [模块 PRD](../PRD.md)，依赖遵循 [共享契约](../../modules/CONTRACTS.md)。

给单语言识别链路一个出口：语音页显示这一段实际按哪个语言识别，点一下能改。[STT-04](../../stt/specs/STT-04.md) 只降低了误入的概率，解不开已经锁死的状态——这一份负责那个出口。

## 为什么必须做

用户实测报告：说日语，识别出来是英文。聊天记录里的证据链完整：

```
21:02  Hello
21:59  konichiwa          ← 说的是「こんにちは」，英文引擎转成了罗马字
22:08  with that shit     ← 英文引擎在听日语
22:08  going to work      ← 同上
```

一旦有过一条纯拉丁的识别结果，语言判定就给出 `en-US`；英文引擎**只可能吐拉丁字母**，于是每一段都在重新确认「这是英文」。同一个闩之前在中文方向上也实测到过。

[STT-04](../../stt/specs/STT-04.md) 的「实现时发现的前提修正」已经论证过：**要从错的语言里出来，需要一条「这是另一种语言」的证据，而错的引擎产生不出那条证据**。单语言引擎加纯文本信号，信息上不可能自我纠正。所以出口只能来自人，或者来自换掉引擎（本地 whisper 的 `language: "auto"`）。

这不推翻 PRD 的「不需要用户参与」：默认路径仍然是自动跟随，这个控件是纠错入口，不是让用户在说话前先选语言。

## 取舍

**为什么是循环按钮而不是下拉**：只有三种语言，循环点击比下拉少一次交互，而且语音页是全屏沉浸态，塞一个 select 进去很突兀。代价是从日语到英语要点两下。

**为什么指定只在本次语音页有效**：它是纠错而不是设置。而且用对的语言说一句之后，判定自己就能跟上（识别结果里有假名了），指定就不再需要——把临时纠正变成永久设置反而会在用户真的换语言时挡路。退出即失效，下次进来仍然自动跟随。

**为什么点下去要立刻重开识别**：用户点它的时候正卡在错的语言上。让他再说一句废话去触发下一段切换没有道理，而且那句废话也会被错的引擎收走。

## AC

| AC | 模块内验收 |

| FE-13-A | 快照里 `language` 就是引擎这一段实际收到的语言码，`languagePinned` 初始为 false；页面显示它 |
| FE-13-B | `setLanguage()` 立刻生效：旧那段被 abort，下一段 `start` 收到新语言；此后推导不再被调用，也不能推翻指定 |

| FE-13-D | 页面只转发：`VoiceModal` 不含任何语言判定或顺序逻辑之外的状态，当前语言与是否指定都来自快照 |

## 不在本 SPEC

- **按 Web Speech 的 confidence 自动退回**：有价值（它能在用户没注意时自己纠正），但需要 `SpeechRecognitionResult.confidence` 的真机分布数据才能定阈值，属 [STT-03](../../stt/specs/STT-03.md) 的真机验收范围。
- 混说识别：本地 whisper 的事。
- 把指定持久化成设置项。

只执行当前 SPEC 的本模块测试；其他模块使用 fake/mock。验收报告放 `../reports/FE-13_ACCEPTANCE.md`。全流程测试仅在必须联调或大任务完成时按 [集成 SPEC](../../integration/SPEC.md) 执行；真人设备后置项不自动恢复。
