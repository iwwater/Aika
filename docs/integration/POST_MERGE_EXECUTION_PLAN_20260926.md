- 先在当前合批分支做 P0 的定向修复与文档收口，保持原 `master` 工作区原样；每个工作包独立提交，规范/状态文档与业务代码分开提交。提交前核对文件清单，推送前核对分支和远端，不强推。
- 代码合批后的下一次合入目标需由 P0-1/P0-3 的准入结论决定。若根许可证范围、敏感内容或两端交付边界未清楚，保留审阅分支，不宣布可发布。创建 PR 可以承载审阅，但 PR 通过不自动代表 0.79、0.81、0.82 的版本验收。
- 每个实现工作包开始前选对应模块现有 SPEC；若缺 SPEC，先补一份最小规格及 AC。仅运行受影响模块的测试；到明确的集成或发布里程碑才扩到全量构建与设备矩阵。
- 本计划的净工时只作排序参考：已执行 P0 的历史估计不再计入剩余工作；Tauri P1 约 1.5～4.5 天主动工作，Next N1 约 4～9 天另行排队，外部授权与自然试运行另计。P2 不计入当前排期。
