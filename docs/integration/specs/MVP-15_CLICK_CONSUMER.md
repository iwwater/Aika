# MVP-15 · 点击的 Aika 侧语义（消费者 SPEC）

依据：[MVP-12 §4 不预定项](MVP-12.md)、[RPD_MVP_0.6 §4 MVP-R12](../RPD_MVP_0.6.md)、[共享契约 §8](../../frontend/DESKTOP_PET_CONTRACT.md)。
状态：**草案，未派发实施**。v1（记录 + 诊断）已随 MVP-12 落地并被本 SPEC 冻结；v2 语义**待用户拍板**（§5）。

## 0. 这份 SPEC 解决什么

MVP-12 把「用户点了宠物」这个事实从 pet-shell 送到了 Aika 就停了：Aiki 侧只承诺
「收到已授权的点击事实、按 `eventId` 去重、由明确登记的消费者处理」，**消费者做什么另立 SPEC**——
本文就是那份 SPEC。

现状说明（不是遗漏）：点击今天到达 Aika 后**没有任何产品行为**。这是 MVP-12 明确不预定的范围，
不是实现缺失。本 SPEC 要决定的是「要不要有、有什么」，以及一旦有，边界在哪。

## 1. v1：只作为可观测事实（已实现，本 SPEC 冻结）

| 项 | 冻结值 |
| --- | --- |
| 事实入口 | Rust 接收端受理后 `emit_to("main", "pet://click", 事件体)`；**只发授权主窗** |
| 消费者 | 诊断计数（Aiki 侧 `pet_click_diagnostics`）+ 主窗事件监听位；**没有产品行为** |
| 不生成对话轮 | 不创建会话、不调 provider、不写记忆、不进 outbox |
| 不命令宠物做动作 | Aika **不**用 `action/emotion` 回应点击——shell 本地的 `clickAction` 已经在播动作，双重动作会打架 |
| 不进入 Trace | Trace 是**轮次内**事件流（`record(turnId, …)`，`seq` 按轮编号）。点击不属于任何一轮，塞进去会破坏「seq 一轮内单调递增」这条不变量 |
| 频控 | 由 shell 侧折叠（位移 <4px 才算点击、400ms 冷却）与去重（Aiki 侧按 `eventId`）；Aika 侧不额外排队 |
| 可关闭 | 未注入凭据 = 子进程零请求；未武装 = Aiki 一律 403 |

**AC-1（v1，可验收）**：点击到达时 Aiki 计数 `accepted` 递增且每个 `eventId` 只计一次；
重复投递 `duplicates` 递增而 `accepted` 不变；未武装时 `unarmed` 递增。证据见
[MVP-12 报告](../reports/MVP-12_ACCEPTANCE.md) §5.1/§5.2 与 §6 的 Rust 真 socket 测试。

## 2. 与既有机制的关系（为什么不能随手接）

写清楚这一点比选功能更重要：Aika 里已经有几套「什么时候可以说话」的判断，接错一处就会绕过它们。

| 既有机制 | 能不能用来承接点击 | 理由 |
| --- | --- | --- |
| `TraceRecorder`（LLM-06/07/08） | **不能** | 轮次内事件流，无 `turnId` 的点击不属于它（见 §1） |
| `EnvironmentEvent` + `RuleProactivePolicy`（FE-22） | **不直接接** | 其事件语义是屏幕/窗口/游戏状态（`foreground_changed`/`screen_keyword`/`game_event`），阈值是为「弱信号累计」设计的。把点击塞进去等于把「用户碰了一下桌宠」和「屏幕内容」混成一类，且会继承 `userBusy===null ⇒ ignore` 这条对点击不合理的规则 |
| `canSend`（presenter 终审） | **可以复用** | 「现在能不能说话」的唯一出口。任何 v2 选项要说话，都必须过它，**不许新造第二套判断** |
| `busySource` / MVP-03 陪伴状态（主动/安静/…） | **必须遵守** | 「安静」是用户显式表达的意愿，优先于任何点击触发 |
| `DeliveryPolicy`（RT-06） | 不适用 | 它管的是跨渠道主动消息投递（授权目标、群组红线、quietHours 暂缓），不是本机即时回应 |

## 3. v2 候选语义（待拍板）

四个选项互不排斥，可组合；但**每次只落一个**，落一个就写一节 AC 并单独派发。

### 选项 A：维持零行为（= v1，只是把它写成承诺）
- 成本 `0`；风险 `0`；点击只作为可观测事实与未来能力的接口。
- 适合：现在不想让桌宠多说话。

### 选项 B：受限的轻量回应（**2026-09-16 用户拍板采用**）
- 语义：点击 → 一句短回应。**先走固定短语池 + 本地 TTS，不调 provider**（于是零 LLM 成本、零外发）。
- 必须同时满足：过 `canSend` 终审；冷却 ≥30s；安静模式一律不说；连续点击只在冷却后回应一次（点击**不排队、不累计**）。
- 成本：一次本地 TTS（可关）。风险：低——最坏情况是「说了句废话」。
- 后续可选升级为 LLM 生成的一句话，但那要另立一节 AC 并重新评估成本与延迟。

**两个新方法的边界（同时改动了 Presenter 契约）**

| 方法 | 规矩 |
| --- | --- |
| `CompanionPresenter.canSpeakAside()` | 与主动消息**同一份** canSend 输入与同一个纯函数；**不建轮、不写库、不计数、不通知**。唯一差别：**不要求 provider 已连接**（插一句话不需要模型，离线也能「嗯？」一声） |
| `VoicePresenter.speakAside(text)` / `isSpeaking()` | 与朗读消息同一套说话权规则：会话开着不抢、正在念不叠话；**不设 `speakingMessageId`、不碰字幕**（它不是为了「正在朗读某条消息」而存在的） |

**架构约束（踩过才知道，写下来免得下次再踩）**：Presenter 的工厂在 `starting` 期间解析会抛
`kernel is starting; call start() first`，而 `PluginContext.registrar` 在 activate 返回后即被 revoke。
所以本插件**不在 activate 里解析 Presenter**，而是由组合根注入一个「启动后解析器」
（`HostOptions.resolve`，组合根本就是白名单里允许调用 `registry.resolve` 的地方），
在**点击真的发生时才问**。时钟这类普通服务仍走 registrar（activate 期间合法）。

**⚠️ 尚未验证的那一层**：以上是模块与接线层的证据（单测 + 真实内核）。**真正按一次桌宠听到她开口**要问你的耳朵——本轮我只能在真实应用里验到「事件到达 + 出声调用被触发」这一层（见 §6）。

### 选项 C：点击 = 开一轮对话
- **MVP-12 已明确排除「默认点击生成一轮对话」**。只能作为**用户显式开关**（默认关）。
- 若要做，必须解决：连击去重（400ms 折叠后仍可能连点）、误触成本（一轮对话可能要花钱）、安静模式下是否静默入队。
- 这一项本质是把桌宠变成「对话入口」，属于产品定位决策，不由执行者代拍。

### 选项 D：把点击当作「用户在电脑前」的在场信号
- 语义：点击 → 更新在场/活跃度，供主动消息更自信地决定「现在说合不合适」。
- **这是本 SPEC 唯一带隐私风险的一项**：它把「鼠标碰过桌宠」变成对用户状态的可推断信号（甚至能推断在不在座位上）。要做必须同时满足：
  1. 显式授权（默认关，且不与其他开关捆绑）；
  2. 有一条明确的、可读的说明告诉用户它被用来做什么；
  3. **绝不出本机**：不写进任何外发内容、不进任何 provider 请求、不写入可被导出给第三方的字段；
  4. 可一键清除（清空计数与派生状态）。
- 建议：**单独立项**（隐私口径先写清楚再谈实现），不与 B 捆绑。

## 4. 无论选哪个都必须满足的不变量

v2 落地时逐条转 AC：

1. **零新外发**：点击本身不得产生任何新的网络外发（选项 B 的固定短语池也不调 provider）。
2. **频控与上限**：任何回应的最小间隔与单位时间上限是显式常数，写进 SPEC 并可测。
3. **状态优先**：安静/忙/陪伴结束 状态优先于点击触发；被抑制**必须可计数并带原因**（不是静默吞掉）。
4. **关掉即零成本**：关闭选项后不构造事件、不读时钟、不调 TTS，且 shell 侧保持零请求。
5. **不打架**：不得与 shell 本地 `clickAction` 同时表现（同一动作播两次）。
6. **可观测**：收到多少、回应多少、被抑制多少（按原因分）都能从诊断读到。

## 6. 边界（不在本 SPEC）

- **文件输入（拖文件）**：MVP-12 范围冻结时明确不启用（AC-D 记「不适用」），本 SPEC 不重启它。
- **多显示器/高 DPI 下的点击一致性**：属 MVP-13 的真机矩阵。
- **点击的音效/触觉反馈**：shell 侧表现层，不属 Aika 消费语义。
