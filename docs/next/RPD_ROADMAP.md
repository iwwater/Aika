## 1. 产品目标

以 AAAAGENT 已有运行流水线为底座，逐步接入 Aika 的 Provider、Timeline、记忆扩展、感知和表现能力，得到可测试、可替换、可持续维护的陪伴助手。旧 Aika 是行为、素材和实现参考库，不再承担新架构主线。

Aika Next 是运行平台，不把自设计的 Aika/Aiki 人格写死为所有角色的底色。自 0.7 起，通过 Character Distiller 提炼插件，从用户指定的 Wiki、小说或设定文本生成可追溯、可版本化的 Character Pack。角色带着原作赋予的经历，与用户继续形成独立的陪伴经历；两者共同影响互动、表达和关系。

用户侧维护精炼、可纠正的 User Soul；普通对话保存在 History DB，重要内容逐步沉淀为 User Wiki。Character Wiki 则负责角色自身知识的有据补全。平台区分原作事实、推断和用户自设，不把模型生成的故事自动当作真实共同经历。

首要使用平台 Windows 11。源码可在本地构建，模块可在无真人输入的情况下自动测试；一般版本完成开发后集中人工验收；0.75 前端重写例外，必须先逐界面询问改造要求、随后索取参考图，重写后主动提交用户审核，通过后才进入下一界面。上游已有测试不代表本地基线或未来扩展自动通过。

## 2. 架构边界

```text
文本 / 音频 → 输入适配 → 上游轮次与作用域 → 上游对话流水线
                                    ↓
                              Context / Memory
                                    ↓
                             DialogueProvider
                                    ↓
                      回复 → 展示 / TTS / Timeline
```

- 上游轮次、取消、记忆维护、上下文和工作路由优先保留。缺少扩展点时，先以失败契约用例证明，再做最小接口改动，不复制第二套运行时。
- Aika 独有能力通过端口/适配器接入。旧 Plugin Kernel 不迁入；0.65 基于现有 Runtime/Pipeline 提取受约束的编排能力，满足用户自定义全流程的需求。
- Timeline 是事件记录，Memory 是长期记忆策略，Wiki 是知识组织；三者可共享来源标识，但不得重复承担同一职责。
- Context 扩展与对应能力一起交付，不能积累多个未接入主链的孤立模块。
- 角色配置不等于动态关系系统；基础语音不等于音色克隆、声学优化或唤醒。

0.65 先交付内核 + 普通包（桌宠/LLM/文字）、能力包按需导入加载、兼容流程与 Flow Profile 受控编排，复用唯一轮次/取消权威。0.7 再通过其实际扩展入口增加连续性层，不另建对话 Runtime：

```text
Wiki / 小说 / 手动设定 → Character Distiller → Character Pack
                                     ├ Character Soul / Style
                                     ├ Character Wiki
                                     └ Canon Timeline

既有对话 / History DB → Companion Timeline → 既有 Memory 生命周期扩展
                                             ├ User Soul / User Wiki
                                             └ Relationship State

角色底色 + 相关原作知识 + 用户画像 + 共同经历 + 关系状态
                   ↓ 有预算的 Context 组合
             既有 DialogueProvider → 回复 / 基础语音
```

| 概念 | 唯一职责 |
| --- | --- |
| Soul | 稳定的性格、价值取向、互动偏好；与事实条目分开 |
| Wiki | 有来源的角色知识和用户长期事实及其变化 |
| Canon Timeline | 指定作品版本与剧情进度内的角色原作经历 |
| Companion Timeline | 当前用户与当前角色实例实际发生的陪伴经历 |
| Memory | 从历史选择、维护、纠正、遗忘值得保留的内容；保留上游生命周期 |
| Relationship | 当前用户与角色实例之间有证据的互动适应 |
| Context | 决定当前轮可用的信息与预算，不把整个库塞进 Prompt |

提炼“插件”指可替换的来源/提炼适配器与统一 Character Pack 协议，不要求迁入完整 Plugin Kernel。关系适应叠加于角色底色，不能自动重写原作。双时间线不混用现实日期和剧情顺序；来源撤销、遗忘和角色切换须贯穿所有派生数据。

## 4. 开发与 Git 路线

本轮仅提供[合作者模块规范](../development/PLUGIN_DEVELOPMENT.md)，STT/TTS/情感陪伴新模块由各负责人开发；主线负责已有能力迁移与集成。DSH 分发保留[后置意向](../integrations/dsh/README.md)，不增加当前验收范围。

按用户确认的[连续执行计划](EXECUTION_061_065.md)，0.61 自动收口并冻结基线后进入 0.65。用户后续允许 K65-11 的 32 项人工验收暂缓并推进 0.7，原编号与未验状态保留。后续独立模块可先开发，依赖的实际接口/自动门槛仍须满足；暂缓不是 ACCEPTED。

`aika-next` 从独立历史的文档种子开始，NEXT-00 已记录上游历史引入与固定基线，详见 [BASELINE](0.6/BASELINE.md)；不与旧 master 混合。所有后续功能分支从该新主线派生，例 `feat/next06-provider`；通过本 SPEC 自动门槛和 diff 审阅后回到新主线。

0.61 执行前固定 0.6 实际交付提交，依次完成修复 SPEC。0.65 实施前固定 0.61 实际交付提交，核对流程与生命周期；0.7 实施前以 0.65 实际交付提交重新核对接口和数据模式；0.7 迁移须兼容 0.6 数据升级来源及 0.61 知识库、模型配置和快照。后续兼容适配由对应版本承担，不要求当前 0.6 worker 预先搭骨架。

版本开发过程中，新主线允许集成已通过的增量；发布以通过人工验收的版本提交为准，不要求把全部远期能力完成后才首次发布。若未来改名为新仓库 main，另行操作；禁止将 orphan 分支直接合入旧 master。

## 5. 统一完成定义

1. 模块完成：本模块 AC 自动通过，相关回归通过，有证据，待集成项明确。
2. 版本开发完成：版本所有必需自动门槛通过、必要构建可用，可交用户验收。
3. 版本验收完成：用户确认真实使用结果；需修复的问题补测试后修复，再定向复验。
4. 发布：对应验收通过提交，记录版本与来源；推送、分发由后续明确授权决定。

既有语音/文字用例优先复用。新行为要新增必要失败测试；不能因“只用既有测试”而放弃对新增行为的验证。

## 6. 主要风险与出口

| 风险 | 处理与出口 |
| --- | --- |
| 上游 Windows 与 macOS 能力不同 | NEXT-00 先核实 Windows 路径、构建和可用性，不跨平台复制假设 |
| 原测试耦合旧 Kernel/Runtime | 复用行为、输入和预期，改 harness；不为了跑旧测试把旧架构搬入 |
| 模型随机性或服务不可用 | fixture 确保逻辑确定性，真实回放单列；必需真实门槛未跑不宣布开发完成 |
| 数据误覆盖 | Next 使用独立用户数据目录；旧数据库导入不在 0.6 范围 |
| 上游扩展点不足 | 记录最小变更、上游差异和契约测试，不大改核心 |
| 来源/资产限制 | 导入保留 LICENSE、版权与来源；本路线不承诺商业可分发性 |
| 角色知识混线或超过剧情进度 | Character Pack 绑定作品版本、角色与知识截止点；原作/陪伴、已知/未知分别标记 |
| Soul/Wiki 内容自我强化 | 推断必须带证据，生成的回复不是事实证据；重复重放不增加证据权重 |
| 长期记忆无法真正遗忘 | 来源到 Memory/Soul/Wiki/关系及索引可追溯，撤销后不被后台重建恢复 |
