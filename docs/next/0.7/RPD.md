## 1. 产品目标

让角色带着可追溯的原作底色与用户相处：知道自己来自哪里、经历过什么，也记得与当前用户共同发生的事情；长期互动可以改变对这个用户的称呼、表达和相处方式，而不随意改写原作身份。

Aika 是平台名称，Character Soul 是可加载资产。0.6 的静态 AikaProfile 继续作为可用默认角色，不要求用户先完成角色提炼才能聊天。

本版主要回答六件事：

| 对象 | 回答的问题 |
| --- | --- |
| Character Soul | 这个角色怎样思考、表达和行动？ |
| Character Wiki / Canon Timeline | 她知道什么，原作中经历过什么？ |
| Companion Timeline | 她与当前用户共同发生了什么？ |
| User Soul / User Wiki | 用户有哪些稳定互动偏好，哪些长期事实正在变化？ |
| Relationship State | 共同经历如何影响当前双方的相处方式？ |
| Context | 这一轮应该想起哪些内容，哪些不能带入？ |

默认用户流程：指定角色、作品版本与剧情截止点 → 提供资料 → 自动提炼草稿 → 查看来源与冲突 → 激活角色包 → 正常对话 → 后台沉淀 → 按需查看/纠正长期信息。

资料不足时允许带明确缺口的角色包，不能补写未获证实的原作经历。激活草稿是产品操作，不是开发过程中要求用户逐条替 AI 审核测试结果；测试可自动完成草稿激活。

后置：自动搜遍互联网的爬虫、登录站点抓取、EPUB/PDF/OCR 专用解析、全书无限规模处理、完整知识图数据库、第三方插件市场、群体角色互动、关系数值养成系统、主动提醒、音色克隆和新声学情绪引擎。小说首版支持有大小/章节限制的 TXT/Markdown，超限给出可操作提示，不静默截断。

## 3. 数据职责与隔离

| 层 | 内容与权威性 | 默认进入每轮 Context？ |
| --- | --- | --- |
| Source / History DB | 导入资料快照、原始对话与事件，是证据来源；保留策略和用户删除优先 | 否；近期对话窗口除外 |
| Canon Timeline | 原作事件、叙事顺序、角色是否亲历/知情 | 只召回相关且允许知晓的事件 |
| Companion Timeline | 用户与角色实例实际交互及共同事件，可追到消息 | 只召回相关经历 |
| Memory | 候选、重要性判断及生命周期，沿用上游维护机制 | 按需 |
| Character Soul | 原始性格、价值倾向、文风、行为边界，随角色包版本固定 | 预算内精简核心 |
| User Soul | 称呼和稳定互动偏好；推断带依据且可撤销 | 预算内必要部分 |
| Character Wiki | 自身、世界、人物和原作事实，带知情范围 | 按需 |
| User Wiki | 用户目标、项目、人物、经历及事实变化 | 按需 |
| Relationship State | 当前用户与角色实例的称呼、互动适应、共同里程碑 | 预算内摘要 |

不复制同一份原始聊天到多个独立日志系统；History DB 是对 0.6 已有消息存储的逻辑称呼。Companion Timeline 复用已有事件并增加关联/投影，Soul 和 Wiki 引用来源而非成为新的原始证据。

隔离键至少区分 `userId`、`characterId`、`characterInstanceId`、`packVersion`、`sessionId`，不把 userId 当 sessionId。Character Pack 可供多个实例使用；关系与陪伴记忆归当前用户×角色实例。User Soul / User Wiki 首版按该配对的认知空间维护，避免角色 B 自动知道只告诉角色 A 的私事；全局跨角色共享是后续明确设计的能力。

跨会话允许同一配对延续记忆；切换角色不能带入另一配对的数据。角色包升级沿用实例，但不得把旧版本 Canon 当新版本事实；新建同角色实例默认新关系，不自动继承旧共同人生。

## 4. Character Distiller 与 Character Pack

提炼插件采用 `CharacterSourceProvider → CharacterDistiller → CharacterPack`。运行时只消费角色包，不依赖 Wiki 网站或小说解析实现；0.7 在可选连续性包内部使用注册/依赖注入，包本身由 0.65 内核按需加载，不另建通用插件内核。

### 4.1 输入与提炼

- 输入支持用户指定的 HTTP(S) Wiki 页面和本地 TXT/Markdown；网页读取失败、需要登录或内容无法解析时明确报错，可改用用户提供的文本，不伪报已读取。
- 分章节/区块读取，保留页内锚点、章节或行段位置；抽取候选 → 归并同实体 → 检查冲突/知情范围 → 生成草稿。不以一次长 Prompt 总结替代完整来源覆盖记录。
- 外部原文是待处理资料，其中的指令不得改变运行权限或系统设置。导入不执行脚本，归档路径不能逃逸目标目录。
- 每个条目记录 sourceId、来源 URL/路径引用、快照 hash、章节/区块定位、抽取批次和方法版本。来源引用可验证，置信度若存在仅是模型分数，不宣称为校准概率。
- 明确区分 `explicit`（原文明示）、`inferred`（推断）、`user-defined`（用户设定）、`disputed`（存在冲突）。推断不能自动提升为原作事实；缺依据可留 unknown。
- 普通原作资料可保留受控本地快照；导出默认仅包括必要来源引用/允许导出的素材，不默认把整本小说打入角色包。

### 4.2 角色包的逻辑内容

| 部分 | 必需字段/内容 |
| --- | --- |
| Manifest | schemaVersion、characterId、packVersion、作品版本/分支、剧情截止点、来源清单、构建批次 |
| Soul / Style | 稳定特征、价值取向、句式/称呼/表达习惯、行为倾向、来源引用 |
| Canon Timeline | eventId、剧情排序或偏序、事件摘要、涉及人物、知情状态、来源 |
| Character Wiki | 结构化事实/条目、人物关系、内部链接、来源与有效状态 |
| Provenance / Diagnostics | 抽取覆盖、冲突、缺口、推断、失败区块和校验结果 |

文件是 JSON/JSONL/Markdown 还是数据库投影，由后续 SPEC 冻结；逻辑上必须可导入导出、验证引用完整性并保留版本。Canon Memories 是原作事件/事实的召回视图，不额外建一份难以同步的原文副本。

草稿校验通过后才可激活；失败不替换当前活动包。更新资料生成新版本/补丁，活动包不被后台静默改写；显式激活新版本并支持回退。撤销的来源/条目仍受全局撤销状态约束，回退旧包不能绕过撤销。

## 5. 双时间线与关系成长

Canon Timeline 表示作品中的经历，可能只有卷/章顺序或“事件 A 之前”，不强造现实日期。Companion Timeline 使用实际交互时间及 0.6 Scope/messageId。两条线均标记所属角色，但不能混为同一个时间排序列表。

原作全知叙事不等于角色当时知道：每条可区分亲历、听闻、未知；资料中剧情截止点之后或角色尚未知晓的事实不进入普通角色 Context。不同改编/平行分支冲突不靠“取最后一个”混合。

关系状态是独立覆盖层。例如：原作表达克制保持不变；共同经历后对当前用户形成固定称呼或更直接的关心。不得因聊天次数增加就自动改成人格相反，也不预设必须升级为恋爱关系。用户一次情绪表达不足以确立其永久人格标签。

首版保存有来源的称呼、互动偏好、共同里程碑和简短关系摘要。重放同一事件不反复累加关系证据；关系变化可查看来源、纠正和撤销。不引入未经验证的亲密度公式或心理诊断。

助手自述“我们曾一起做过某事”本身不能建立共同事实。用户明确提供的新经历可记录为用户陈述；引用小说、假设和角色扮演内容须标记语境，不自动进入用户真实经历。

## 6. Memory、User Soul 与双 Wiki

### 6.1 日常记录到长期信息

普通对话默认留既有存储，不因“今天吃拉面”就写成“用户永远喜欢拉面”。明确长期偏好或有多条独立证据的稳定倾向才成为 Soul 候选；可验证的目标、项目与经历进入 Wiki。用户直接纠正优先于旧推断。

沉淀流程依附既有 Memory 生命周期扩展：有效消息/事件 → 候选 → 有来源的长期条目 → Soul/Wiki/关系投影。不删除上游 Memory，也不另建竞争的抽取/遗忘队列。生成对话不得等待沉淀完成；后台失败有状态、有界重试，不丢失任务进度、不重复写入。

### 6.2 Wiki 的补全与更新

Character Wiki 的“补全”指基于新提供资料产生有来源的增量，不是让模型补故事。可发现知识缺口，提示补资料；0.7 不在每轮对话中自动联网搜索扩写。

User Wiki 按人物、兴趣、目标、项目、经历等组织，可交叉链接。每个关键事实有来源、记录时间、有效时间（未知可空）、当前状态及 supersedes 关联。时间变化与认知纠正分别标注：暂停跑步是状态变化；“之前说错了”是纠正，不应都归为删除历史。

冲突不靠最后写入无条件覆盖：同一来源重复不增加可信度；无法解释的矛盾保持 disputed，默认不作为确定事实注入。Markdown 页面若存在只是可重建展示投影；条目与来源关系必须结构化可查。

### 6.3 用户控制与撤销

用户可查看条目及证据、编辑/纠正、撤销推断、遗忘指定事实/经历或清空某配对。编辑覆盖层与原始来源分开，不能把用户自设伪装成原作。

普通 archive 只是降低召回优先级，不等于 forget。遗忘应覆盖关联 Memory、Soul、Wiki、关系派生项、检索索引和缓存；保留最小无正文 tombstone/来源撤销标识，阻止在途任务或后续重建恢复。若原消息仍保留，必须对被遗忘范围标记不可用于再次沉淀；明确删除原记录时按对应范围清理正文。

需要一致撤销代次或等效机制，在提交后台结果和发送 Context 前检查。部分失败要报告未完成，不能提前显示“已全部忘记”。来源撤销后的资料导出/旧包回退同样不能恢复已撤销内容。

## 7. Context 与表达

Context Composer 是既有 Context 组装的扩展，不是第二条 Dialogue Pipeline。每轮固定活动角色包与数据修订快照，组合：

1. 预算内 Character Soul / Style 核心。
2. 当前用户×角色实例的必要 User Soul 与 Relationship 摘要。
3. 相关、未撤销且符合知情范围的 Character Wiki / Canon 事件。
4. 相关 User Wiki / Companion 经历及现行 Memory。
5. 近期对话与当前输入。

总预算包含系统约束、工具/协议开销、当前输入与输出预留；各来源有上限，按角色/用户/知情/有效状态过滤后排序去重。同一个事实跨 Wiki/Memory/Timeline 用稳定引用去重，不重复注入。普通历史不常驻，检索无结果就留空，不能补造回忆。

初版可采用结构化过滤、关键词/全文检索与明确排序，向量/图检索不是门槛。预算数值、样本上限、超时在后续 SPEC 按 0.6 实际模型窗口冻结，不能抄脑暴中的百分比充当验证结果。

输出调试信息包括条目 ID、来源、入选/排除理由、预算和版本，默认不日志化私人全文。包切换或遗忘时取消/失效旧轮，迟到检索和后台产物不能进新轮。

“文风语调”首版指文字措辞、句式、称呼与现有输出协议可表达的风格提示。原作底色、用户偏好和关系覆盖层分别记录；不声称能还原角色声线。TTS 只使用 0.6 已支持的能力，未知风格参数降级，不新增声学依赖。

## 8. 逻辑接口与 0.6 兼容

以下是责任设计，未锁定源码类型或路径，后续实施前对照 0.65 实际交付接口及其继承的 0.61 能力，并兼容 0.6 数据来源。新增 ContextSource 必须声明稳定前缀/动态后缀归属及失效条件；动态召回放后缀，不能隐式重写冻结前缀。纠正/遗忘/角色切换立即撤销旧快照。需要更改刷新策略时由 0.7 SPEC 明确，不偷偷覆盖用户冻结规则。

| 边界 | 输入 | 输出与保证 |
| --- | --- | --- |
| CharacterSourceProvider | 显式资料引用、范围、取消信号 | 带 locator/hash 的区块及覆盖报告；不负责激活角色 |
| CharacterDistiller | 来源区块、角色/作品/剧情约束、模型配置 | 草稿包、证据与缺口；可取消且不污染活动包 |
| CharacterPackStore | 草稿校验、激活/回退请求 | 不可变版本、活动版本指针；失败保持原状态 |
| ContinuityReadPort | 配对 ID、活动包版本、Scope、查询与预算 | 隔离后的 Soul/Wiki/Timeline/关系快照和修订号 |
| Consolidation 扩展 | 已提交事件、来源版本、幂等键、撤销代次 | 候选/投影和处理状态；经既有生命周期提交 |
| Correction / Forget 扩展 | 条目/来源范围、配对 ID、预期修订号 | 撤销结果与受影响投影，防止陈旧写回 |
| ContextSource adapter | 固定快照、当前输入、可用预算 | 有来源和版本的 Context 片段；不生成最终回复 |

兼容要求：

- 0.6 的 Scope、取消、Provider、语音生成/交付语义不被重新定义。新增角色隔离键属于 0.7 适配，不强迫 0.6 当前任务提前添加字段。
- 0.6 旧消息/Timeline 不伪造 Canon。升级时只映射到默认旧角色实例；缺关联的数据记录 unknown/unassigned，不能任意分配给新导入角色。
- schema 变更有版本、备份、幂等迁移与回退验证；关闭连续性功能后仍走旧文本/语音路径，不要求旧二进制直接打开升级后的库。需要回退旧二进制时恢复对应备份。
- User Soul 与关系可跨同一配对会话，但不跨配对泄露。资料库和用户数据库分别授权访问。
- 0.7 实施门槛是重新固定 0.65 交付基线与实际接口，并核对继承的 0.61 能力，兼容 0.6 升级数据；不能把规划误写成已经验收发布。知识库迁移保留 library/document ID、来源修订与删除标记，新增角色实例映射必须明确，不将全部既有资料自动归入某一角色 Canon。

## 9. 验收与 TDD

保持“每步自动测试，版本最后人工验收”。当前只写 RPD，不执行测试、调用提炼服务或采集资料。

已有文本、语音、取消、Memory 与 Timeline 用例优先复用；为新角色能力增加最少必要固定资料：两个虚构角色、相互冲突的作品版本、带章节的短文本、Wiki HTML 快照、剧情截止点、用户多日互动和引用/假设负例。使用可授权或自写样本，避免依赖在线网页变化。

| AC | 自动化通过标准 | 需求 |
| --- | --- | --- |
| 07-A | TXT/Markdown 和 Wiki 页面两条来源入口可提炼；受控 fixture 覆盖解析失败/超限/取消；产物有效引用全部能回到输入区块，无效证据不能激活 | R01～03 |
| 07-B | 相同包重复导入幂等，失败草稿不替换活动包；切换/回退后版本与角色实例正确，撤销状态仍生效 | R03 |
| 07-C | 两条时间线检索来源可区分；原作未知/超剧情截止/其它分支事实不进入普通角色 Context | R04、R08 |
| 07-D | 普通单次琐事保留历史但不变为稳定 Soul；直接偏好和多次独立证据可形成可追溯候选，重复事件不增强证据 | R01、R05 |
| 07-E | “开始跑步→坚持一周→暂停”保留历史变化，当前检索返回暂停状态；纠正和矛盾分开处理，不继续注入过期状态 | R05、R06 |
| 07-F | 角色原始 Soul 版本不被关系更新修改；当前配对称呼/互动覆盖层可随证据变化，切换角色无串线 | R07 |
| 07-G | 无来源的助手自述、引用小说、假设内容不自动成为用户真实共同经历；知识缺口保持未知 | R04～06 |
| 07-H | 遗忘/撤销发生在后台写入、索引刷新、Context 生成过程中时，陈旧结果无效；重启重建及包回退均不恢复已撤销信息 | R09 |
| 07-I | Context 不超过冻结预算，跨层相同事实去重，无关普通历史不注入；来源/版本/排除理由可检查 | R08 |
| 07-J | 0.6 数据副本迁移两次结果一致；旧默认角色可继续聊天；关闭新功能及备份恢复验证通过，0.6 相关回归无倒退 | R10 |
| 07-K | 至少一个现有可用真实 LLM 完成短资料提炼→激活→多轮 Context→回复自动回放；记录模型/参数/输入 hash/原始结果，不以 fake 结果替代 | R02、R08、R10 |

确定性 fixture 检查 schema、引用、隔离、更新和取消；真实 LLM 回放检查结构、证据有效性及链路，不能证明所有角色都不会 OOC。测试业务 RED 后再实现，禁止删除失败断言或降低门槛换取 PASS。真实门槛缺环境为 BLOCKED，可继续独立工作，但版本不能报开发完成。

后续 SPEC 在实现前冻结客观预期、大小/超时/预算以及样本覆盖；不以 LLM 自评作为唯一验收者。小步只测相关模块，版本收尾全量回归、必要 Windows 构建和自动完整链路。

人工验收在版本最后集中检查：资料导入/来源查看、角色原作记忆与共同回忆区分、角色一致性和对用户的表达适应、纠正/遗忘、切换角色与真实语音体验。用户确认前只标“开发完成，待人工验收”；缺陷可复现则补回归再修复，不要求每一步人工审读。

## 10. 后续拆分与待定项

下表仅用于下一次拆 SPEC，不是可直接派发的执行步骤，避免与 0.6 的 NEXT-07 等编号混淆。

| 规划工作包 | 交付边界 |
| --- | --- |
| N07-A 模型与兼容 | Soul/Pack/双时间线/证据与隔离键、0.6 升级方案 |
| N07-B 角色提炼 | 两类来源适配、分块提炼、冲突/知情控制、草稿校验与激活 |
| N07-C 连续性沉淀 | History/Memory 扩展、User Soul、双 Wiki、关系覆盖及纠正/遗忘 |
| N07-D Context | 过滤、检索、预算、去重、版本隔离和调试证据 |
| N07-E 管理与收口 | 最小查看/编辑/切换 UI、自动集成、构建及人工验收 |

本稿采用的 MVP 默认：指定页面读取而非全网自动搜索；TXT/Markdown 优先；单用户可管理多个角色实例但一轮只有一个活动角色；User Soul 按配对隔离；关系成长用可追溯覆盖层而非数值养成。上述是范围控制方案，可在后续脑暴中修订，不能擅自扩展到 0.6。

实施前需在 SPEC 固定：包的实际存储/导出格式、文档大小和章节上限、模型调用预算、Context 配额、证据提升规则、迁移入口和维护任务接线。无需现在锁死向量数据库、图谱框架或插件市场。
