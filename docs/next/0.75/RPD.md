## 1. 目标与版本位置

版本顺序为 **0.7 → 0.75 → 0.8 → 0.9 → 1.0**。0.7 提供连续性业务与实际运行接线；0.75 统一重写控制台及桌宠周边全部功能界面，覆盖配置 API、换肤、记忆管理等功能；0.8/0.9 在这个基础上增加新能力。

用户已确认：桌宠右键需要减负，但必须保留；现在只划分步骤和接口。**每个界面实施前必须向用户索取参考，确认复现范围后再逐个重写。** 本文不预设页面布局、配色、组件样式、导航形式、右键条目数量或前端框架。

业务能力存在不等于界面完成，页面存在也不等于后端已接线。现状见 [源码清单](SOURCE_AUDIT.md)，接口见 [CONTRACTS](CONTRACTS.md)，执行顺序见 [SPEC](SPEC.md)。

## 4. 逐界面参考门槛

每次修改某个前端界面前，严格按以下顺序执行，不能跳步或批量替用户决定：

1. **先问改成什么样**：明确询问“这次准备修改【XX 前端/页面/弹窗】，你希望改成什么样子？”，等待用户说明功能、布局和交互要求。
2. **随后索取参考图**：根据用户回答，请用户提供本界面的参考图；实际查看图片后，结合要求确认复现范围。文字说明不能自动代替参考图；只有用户明确表示本次无需图片时才可例外，并记录该决定。不能自行搜索一张图视为用户参考。
3. **按要求重写本界面**：未收到参考图或用户明确的豁免，不开始界面改动。主态、子页/抽屉/弹窗、错误等状态若无参考，先核实处理方式，不自行补设计。
4. **完成后主动找用户审核**：提供实际实现截图、打开/运行方式、与参考的差异及验证结果，明确请用户审核；自动测试通过不等于用户审核通过。
5. **审核修改形成闭环**：未通过则留在本界面，先问清这次要改成什么样、随后请用户提供补充参考图（或明确继续沿用原图），再修改并重新提交审核。用户已给出的具体修改意见可作为本轮要求，不重复问同一问题。
6. **通过后才进入下一界面**：用户明确审核通过后，再对下一界面从第 1 步开始。沉默、上一页批准或全局主题批准均不代表本页通过；禁止先批量重写全部界面再集中审核。

技术库存、接口审计、契约测试和不涉及视觉的基础设施可先做。任何可见布局（包括骨架、导航、通用弹窗）仍受此门槛约束。UI 设计栏在用户提供参考前保持留白；不以默认设计系统填补。

## 5. 架构与实施顺序

目标依赖方向：界面 → 页面应用服务/状态 → 同源 Management API 或受限 Desktop Bridge → 既有业务端口 → 唯一数据/运行权威。HTTP 页面不直接读数据库、启动模型或调用任意 Electron IPC；桌面和控制台共享契约，不共享 DOM 生命周期。

按 [SPEC](SPEC.md) 从接口和入口盘点、控制台壳、右键到各功能组逐个替换。页面业务拆分不等于最终导航拆分；用户参考可以合并展示，但每项能力仍需独立验收。

不预设 React/Vue 等框架迁移。N075-01 根据实际构建、静态资源服务、共享状态和测试成本记录技术选择，选择框架不代表视觉方案获批。不为重写新增第二套配置、角色库、Memory 或对话 Runtime。

## 6. 验收与版本衔接

- 0.7 负责数据模式、业务正确性、生产轮次/后台接线及管理端口；0.75 负责完整管理体验重写。0.7 原 UI 需求由本版承接，不把 API 测试写成旧 UI 已完成。
- 0.65 的 32 项人工验收保留原编号及未验状态；本版对重写界面建立对应关系，真实设备/模型与真人操作未做仍标未验。
- 自动验证检查路由可达、契约/鉴权、作用域隔离、冲突与取消、真实接线、构建及受影响回归；视觉复现须用户逐页验收。
- 未获参考页面不能算开发完成。最终验收以功能清单全覆盖、用户逐页验收、旧入口迁移和无表现层回归为出口。
- 0.8/0.9/1.0 的新增界面继续使用本版参考门槛与基础架构，不提前用虚假成功状态占位。

本次仅形成规划、接口边界及源码核对；没有重写运行代码，没有宣布任何人工验收通过。
