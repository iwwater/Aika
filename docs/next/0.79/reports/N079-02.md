## 1. 8/16 非摘要字段根因排查（基于聚合与时间分析，无正文泄露）

通过只读聚合 SQL、创建时间分析与 Git 历史回溯，定位如下：

1. **存量记录写入时机**：
   - 正式库 `companion.sqlite` 的 `runtime_traces` 表中共 8 条记录。
   - 前 4 条（第 1～4 轮，创建于 2026-09-22 13:18:51 至 13:25:36 UTC）是在引入写入端脱敏提交（`caeff9d`，2026-09-22 15:16:23 UTC）之前写入，`user_text` 与 `reply_text` 当时以明文入库；同时其 `distill` stage 包含未脱敏的 `fact` 字段。
   - 后 4 条（第 5～8 轮，创建于 2026-09-22 16:01:15 至 17:54:30 UTC）写入时已调用 `sanitizeTraceText`，因此入库时字段已是 `[digest:… len:…]`。
   - 故入库字段呈现 8 个非 digest（4 user + 4 reply）与 8 个 digest。
2. **读取与序列化暴露面缺陷**：
   - `RuntimeTraceStore.list()` 和 `RuntimeTraceStore.get()` 此前直接透传 SQLite 表中的 `user_text`、`reply_text` 和 `stages_json`，读取端未做防御性脱敏兜底。
   - `GET /api/traces` 默认列表直接向前端返回了存量明文；UI 收到后也直接渲染，导致前端列表出现 8/16 明文。
   - 点击“查看阶段明细”时，存量 `stages_json` 中的未脱敏 `details.fact` 也会原样暴露。

## 2. 实施方案与改动路径

1. **核心存储与读取脱敏（`core/trace-store.ts`）**：
   - 增加 `TRACE_DIGEST_PATTERN` 与 `ensureSanitizedTraceText(text)`：当文本不符合摘要格式时强制进行 sha256 摘要转换，已是摘要则保持幂等。
   - `record()` 强制通过 `ensureSanitizedTraceText` 存储（`debugOptIn: false` 时）。
   - `list()` 与 `get()` 在读取端增加防御性脱敏：无论底层 SQLite 存有存量明文或异常数据，默认（`debugOptIn: false`）一律输出 `ensureSanitizedTraceText` 后的 `userText` / `replyText`，且对 `stages[].details` 递归执行 `sanitizeStageDetails(details, false)`，彻底封堵列表与阶段详情的默认正文暴露面。
2. **管理端 API 接口加固（`management/server.ts`）**：
   - `GET /api/traces` 显式设置 `debugOptIn: false`。
   - `GET /api/traces/:traceId/content` 保持鉴权与同源校验（Bearer Token + Origin 校验），仅按 `turnId` 从权威 History 存储按需读取正文，返回 `{ status: 'available' | 'forgotten' | 'unavailable', userText, replyText, reason }`。
3. **前端视图防御展示（`management/ui/views.mjs`）**：
   - 增加 `safeTraceSnippet`：即便极端情况下后端返回非摘要，默认态强制掩码为 `[digest:masked len:…]`。
   - 仅当用户明确点击“查看本机历史正文”且 content 状态为 `available` 时展示明文；点击“隐藏正文”或“🔄 刷新 Trace”立即重置并销毁内存正文。
   - 当历史已遗忘或无关联时，明确显示提示信息，正文保持掩码。
4. **存量 SQLite 幂等脱敏与恢复工具（`tools/sanitize-trace-storage.mjs`）**：
   - 提供 `--dry-run`、`--apply`、`--verify` 与 `--restore <backup>` 功能。
   - 执行 `--apply` 前**强制**创建完整快照备份并校验 SQLite `quick_check=ok`；修改后再次运行 `quick_check`。
   - 支持幂等执行：重复运行显示 0 修改。严禁在控制台打印用户对话正文。
