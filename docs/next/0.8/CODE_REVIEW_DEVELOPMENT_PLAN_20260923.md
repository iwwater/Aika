# Aika Next 0.8 开发计划（含 0.79 代码审查）

日期：2026-09-23。审查对象：`aika-next` 工作树（基线 `6d8a725` 加当前未提交改动），重点为 Windows 正式入口 `windows/code/desktop-pet/` 的内存、Trace、运行时与管理 API。前端内部逻辑本轮仅核对接线边界；完整前端大修列入后续工作流。本文是审查与执行计划，不代表缺陷已修复、0.79 已验收或 0.8 已实施。

## 审查结论与处理顺序

| 优先级 | 发现与证据 | 影响 | 修复与验收 |
| --- | --- | --- | --- |
| P0 | `core/trace-store.ts` 的 `sanitizeStageDetails()` 仅处理数组中的直接字符串，数组对象原样返回（约第 81–87 行）。隔离调用 `sanitizeStageDetails({items:[{prompt:'private sentinel'}]})` 返回原文。写入、列表和按 ID 读取均会调用同一函数。 | 嵌套的 prompt、个人事实等可能写入 Trace 并从默认 API 泄露；现有旧数据读取兜底也覆盖不到这类值。 | 递归处理数组、对象、嵌套数组，保留明确允许的标量元数据；为新写入及旧库读出各加哨兵测试，核查存量字段类别并用隔离副本演练清理。正式库清理由独立的影响/备份/恢复步骤执行。 |
| P0 | `app/management-forget.ts` 第 45–85 行对规划器的所有异常（含取消）进入“直接遗忘”兜底，并把每个非记忆来源的完整文本作为 `retainSources` 片段。隔离复现：一条来源文本含“红茶”和其他内容、仅派生一条“喜欢红茶”记忆；规划器抛错后接口仍返回 `applied`，新 active fragment 仍含“红茶”。现有混合来源测试恰因另有共享记忆返回 503，未覆盖这个形状。 | 用户收到遗忘成功，但可检索来源仍保有要求遗忘的内容，是实际的数据删除违约。 | 移除通用 catch 兜底，异常和取消保持失败关闭；若需要无模型遗忘，另立显式且经来源闭包证明安全的策略。增加仅目标、混合来源、异常、取消、重试与重启测试，检查旧来源和新 fragment 中均不存在目标内容。 |
| P1 | `core/platform-files.ts` 第 58–82 行用 `mtimeMs + size` 缓存 Windows ACL 校验；单独更改 DACL 不改变文件内容与修改时间。 | 同进程后续私有文件检查可能把已放宽权限的凭据、管理 session 或导入库仍判为安全。 | 安全读取前重新核验 ACL，或使用可证明随 ACL 变化的权限修订；增加“先通过→只放宽 DACL→再次检查拒绝”的 Windows 测试。 |
| P1 | `memory/continuity-memory-store.ts` 第 133–169 行递归验证父事实仅看 `status`，没有验证父事实的 `validFrom/validTo` 和 `evidenceEligible`。隔离复现：过期父事实不在 Wiki 快照，引用它的派生子事实仍在 Soul 快照。 | 已过期或不合格证据仍可能支撑长期画像与主动邀请。 | 用同一时点递归检查祖先完整可用性，并在写入/读取两端覆盖有效期、资格、撤销、纠正和多级派生；旧库做失效投影回放。 |
| P2 | `app/trial-backend.ts` 的 `onConversationSaved` 将投影异常全部吞掉；若 outbox 暂存失败，已经保存的 History 没有待重试标记。 | Timeline 可永久漏掉已完成对话，运行时没有可观察的积压或修复入口。 | 保持回复可交付，同时记录不含正文的诊断和可恢复游标；增加注入写失败、重启补投影与缺失检测测试。 |

上述 P0/P1 是 0.8 依赖的数据安全门槛。代码审查没有对现有未提交生产代码做修复，也没有改动用户数据。

## 0.79 → 0.8 准入

1. 先处理审查 P0/P1，并对 Trace 旧记录做隔离副本清理演练；正式实例验证默认 API 与 UI 不返回原文。任何真实库写入前固定影响计数、备份、恢复路径。
2. 完成 N079-08 的 User Wiki/Soul 候选生产来源、审阅与遗忘闭包；证明 History、Companion Timeline、Context 和候选资料在撤销后共同失效。
3. 完成 N079-09 的旧库迁移/恢复、实际 Host/Flow 对话调用及长时/时钟门槛。无法完成的能力保持关闭，并在报告中分别标 `BLOCKED` 或 `NOT RUN`；不能把 0.79 标为已验收。
4. 重新运行受影响逻辑/API 测试及真实 Electron 页面验证。本轮 `npm run build` 成功；12 个定向用例中 10 个通过、2 个 Electron 页在当前本机 Chromium 缓存权限错误下未加载页面，需在可用用户缓存环境重验。

可并行推进不依赖长期画像的 0.8 契约、固定图片 OCR/VLM adapter 与临时 Observation；启用长期画像主动邀请和版本联合交付必须等待对应准入通过。

## 前端大修的未来规划

现有 0.75 RPD 已将全前端逐界面重写列为需求，但当前 0.79 现场修复和 0.8 RPD 只覆盖新增能力的最小体验。把完整大修作为独立的 **UI 改造工作流** 纳入 0.8 后续排期，不用本次后端 review 结论替代前端审查：

1. 先确定共享的页面状态、错误/加载、鉴权、历史/Trace 定位和 Desktop Bridge 契约；清理占位页与旧深链迁移清单。
2. 按用户参考逐页改：桌宠气泡 → 展开聊天 → 控制台会话 → Timeline/资料 → 授权预览 → 主动策略 → 总览/诊断 → Work；已有配置、记忆、知识库、外观与右键菜单随后纳入完整覆盖。每页保留真实后端接线，不以 fixture 页面冒充完成。
3. 每页设计与人工确认后再标 UI 通过；统一做键盘/输入法、窄窗与缩放、可访问性、断线/空态、鼠标穿透、旧数据与实际设备回归。

完整大修的视觉范围与版本归属由后续 UI SPEC 固定；在此之前 0.8 核心能力只做必要界面，不把已有前端实现当作长期完成态。与 0.75 RPD 的逐页参考和用户审核要求保持一致。
