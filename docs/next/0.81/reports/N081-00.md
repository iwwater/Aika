### 6.2 并发下的"首次键盘写入停顿"：已定位为测量方法问题

上一轮曾在双来源交错测量中报告"首次键盘写入 320–334 ms（3 次复现）"并记为待查性能项。
本轮定位完成，结论是**测量方法问题，不是产品缺陷**。

**根因**：`Promise.all` 在同一 tick 启动两条循环。图片循环连续同步调用 SQLite 而**不让出事件
循环**，因此键盘循环的**首次 `await`** 必须等整批同步工作结束后才能恢复——计时器把图片批次的
累计阻塞时间记在了键盘首次写入上。

**对照实验**（await 一个什么都不做的 `async` 函数，同时另一任务做同步忙等）：

| 另一任务单次同步耗时 | 被记为"首次 await 时延" |
| --- | --- |
| 1 ms | 24.6 ms |
| 5 ms | 124.7 ms |
| 12 ms | 299.9 ms |
| 25 ms | 624.9 ms |

线性放大关系明确：该数字反映的是**对方的同步批次总时长**，而非被 await 操作的成本。

**孤立测量一致支持该解释**：

| 条件 | 结果 |
| --- | --- |
| `appendKeyboard` 单独调用 | 首次 10.1 ms，其后 7.5 ms，无停顿 |
| 关库重开后首次写入 | 11.8 ms，无停顿 |
| `service.onKeyboardActivity` 串行 | 平坦 ~7.3 ms，max 10.1 ms |
| 两个 store 调用均改为同步（无 await 边界） | max 17 ms，**停顿完全消失** |
| 授权查询 | ~0.02 ms |

关键判别点：**把两个 store 调用都改成同步后，320 ms 不再出现**——证明停顿来自 await 边界，
而不是存储本身。

**处理**：首个样本从百分位统计中排除，同时**保留为 `firstSampleMs` 字段**以便查证。排除后并发
表现为：键盘 p95 **9.18 ms**、图片 p95 **13.37 ms**、最大 **14.3 ms**、`stallsOver50ms = 0`。

**这是一次我自己的测量错误。** 上一轮我把它当作真实产品停顿并登记为待查项，当时给出的理由是
"3 次复现、事件循环延迟为 0"。复现性高并不等于成因正确——同样的调度假象当然会稳定复现。教训
是：**并发测量必须先把被测操作单独测一遍**，否则调度成本会被算到先被 await 的那一方头上。

原始台账保留：`firstSampleMs.keyboard ≈ 325 ms` 仍在报告中可见，读数本身没有被删除。

采集阈值（桶长/TTL/容量等）见 `TEST_PROFILES.md`，与本节的测量阈值分开，不混用。
