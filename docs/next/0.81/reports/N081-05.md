## 4. 剪贴板读取的字节路径

helper 通道（生产路径）严格为：`WM_CLIPBOARDUPDATE` → 只上报 `clipboardSequence` + `observedAt` →
后端收到通知后下发带 `grantId`/`grantRevision`/`sequence` 的 `read_clipboard_image` →
helper 在 `OpenClipboard` 后**再次**比对 sequence，不一致即回 `stale_clipboard` 并放弃 →
一致则把 `CF_DIBV5`/`CF_DIB` 加 `BITMAPFILEHEADER` 写入 `staging/<instanceId>/clip-*.bmp` →
上游只传 `{stagedAssetId, mimeType, byteLength}` →
后端 `consumeStagedAsset()` 校验 id 落在 staging 根内、读取后**立即删除**。

因此**图片字节从不进入 NDJSON**，helper 也无法指定任意读取路径（id 经 `resolve()` 前缀校验）。非图片内容（文本/HTML/文件列表）在 helper 内即判为 `no_supported_image`，不读入内存、不上报为图片。

`ClipboardImageSource.readImageIfCurrent` 是本路径的可注入替身：真实实现走 helper，测试用受控 `readClipboard` 驱动同一套 sequence 复验、重试与格式检查逻辑。

## 5. 关联判定的保守性

合并需**同时**满足：精确内容摘要相等、两侧时间差 ≤ `crossSourceWindowMs`（normal 5 s / smoke 2 s）、来源通道不同、且两侧各只有一个候选（1:1）。任一不满足即降级：

| 情形 | 结论 | 处理 |
| --- | --- | --- |
| 精确等价 + 窗口内 + 1:1 | `same_capture` | 投影合并显示，底层仍保留两条来源记录 |
| 窗口外 | `separate` | 两次不同使用，各保留新事件 |
| 内容不同但 pHash 相同 | `uncertain` | 仅标记，**不合并、不删除** |
| 1:N / N:1 | `uncertain` | 配对有歧义，保留两条 |
| 同通道 | `separate` | 单通道不构成跨源关联 |

底层两条记录不合成不可拆的记录，因此**撤销任一来源后投影可从剩余有效证据重算**（`AC-08105-5` 已验证）。图片在受管资产层可共享（同配对相同字节），但事件身份仍由各自的来源 key 决定。
