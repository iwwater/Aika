# Aika Next 0.85 RPD · 陪伴 Wiki 编纂与检索质量

版本：0.2；日期：2026-09-23；状态：产品需求与 [N085-00～06 执行 SPEC](SPEC.md) 已编写，均未实施。本版排在 [0.8](../0.8/RPD.md) 后、[0.9](../0.9/RPD.md) 前；不以文档存在证明上游能力已经完成。讨论来源：[对比设计与剪枝](chatgpt-conversation://6ab2f7fe-4c7c-83e8-acc7-4d5137b9eb8f)。其中“来源 → 编纂 → 相互关联的条目 → 查询”作为设计参照，不把讨论中的示例或对外部项目的概括当作已核实的工程事实。

## 1. 定位与版本边界

0.7 已定义 Character Soul、User Soul、Character Wiki、User Wiki、双时间线、关系覆盖、来源与遗忘；0.79 正补正式消息到候选/投影的生产链；0.8 规划授权 Observation、多来源事件与主动邀请。0.85 在这些**真实可用的输入**上解决三个问题：哪些经历值得长期整理、相互矛盾或变化的内容怎样更新、对话时怎样只取当前相关且可信的内容。

用户应能说出“你还记得我最近在忙什么”，获得有时间范围的回忆；问“这个角色为什么这样说”，能区分原作依据、角色表达风格与双方共同经历；在资料页看到来源、修正错误并确认修正已影响下一轮。这里的 Wiki 是陪伴运行时的长期认知资料层，不是另一个对话引擎或通用百科产品。

选择独立的 0.85，是因为 0.8 的主线已经包含采集、事件、邀请、Work 和聊天界面，继续塞入 Wiki 编纂会使其验收失焦；0.9 则聚焦语音和表现。0.85 可以先对既有历史与角色资料做受控整理，但来自屏幕观察的长期沉淀，必须等 0.8 对应授权、保存与撤销链真正可用。0.9 的语音链不以 0.85 全部完成为硬前置。

## 2. 用户流程与数据职责

```text
History / 已授权事件 / 角色资料
    → 既有 Memory 生命周期与 Character Distiller
    → 有证据的候选及冲突检查
    → User Wiki / Character Wiki / Soul 覆盖 / Timeline 投影
    → 分域检索与 Context 预算
    → 当前角色的回复及可查看的来源
```

| 数据域 | 权威与用途 | 0.85 的处理 |
| --- | --- | --- |
| History / Source / 0.8 Event | 原始证据及各自保留、删除权限 | 引用有效来源；不复制成第二份永久原文库 |
| Companion / Canon Timeline | 实际共同经历 / 原作剧情顺序 | 按时间与知情范围检索；Wiki 可引用事件，不以页面替代事件权威 |
| Character Soul / Character Wiki | 活动 Character Pack 的稳定风格 / 有据原作知识 | 新资料先生成草稿与包版本，不能由日常对话静默改写原作 |
| User Soul / User Wiki / Relationship | 稳定互动偏好 / 变化中的用户事实 / 当前配对适应 | 候选、纠正与现行状态由既有连续性维护入口负责 |
| Knowledge Library | 用户导入的外部资料 | 保留独立来源及检索域；不能把文章内容写成用户亲身经历 |

| 对标思路 | 在 Aika 中的取舍 |
| --- | --- |
| Raw Source → 编纂 | 复用 History、来源快照和 0.8 有效事件；编纂只生成可撤销的派生项 |
| Typed Knowledge / Provenance | 用现有 Soul、双 Wiki、双 Timeline、关系域和来源 ID，不把所有内容压成一种 Memory |
| Cross-link / Supersession | 保留少量稳定关联及当前/历史状态；不另建完整知识图谱 |
| Markdown Wiki / 通用百科 | Markdown 仅作可重建阅读视图；优先服务陪伴回忆与角色知情，不建设海量文章库 |

术语沿用 [0.7 RPD](../0.7/RPD.md)；“User Soul”不是另建一份与 User Wiki 竞争的用户传记，“Raw Event 不可修改”也不能覆盖用户删除、来源撤销与保留期限。原始记录的权威、有效性和可删除性以其所属存储为准。

### 3.1 编纂和更新

沿用 0.7 的候选、激活、纠正、遗忘和 Character Pack 提炼/激活流程，不创建第二个定时 Memory Extractor。编纂可以把同一有效来源归纳为便于查找的条目或页面投影；每条关键事实必须能回到具体消息、事件或资料区块。助手自己的回复、引用文字、假设句、Work 工具输出与模型自评不能单独成为用户经历证据。一次“今天压力很大”是短时状态，不能直接写成稳定人格。

首版只建立有用的类型与显式关联，例如“考试目标 ↔ 准备事件”“角色事实 ↔ 原作人物”。关联引用稳定 ID 和来源，不要求全局实体消歧或图数据库。可以生成 Markdown 阅读视图，但结构化条目与来源关系仍为权威；重建视图必须遵守撤销状态。

新证据到达时先比较现行条目和来源：重复来源不增加权重；日期或阶段变化标为时间状态更新；用户明确说错了走纠正；未能解释的矛盾保持 disputed，默认不作为确定事实注入。覆盖记录保留可审计的版本链，不能用“最新一条总是正确”代替判断。用户直接纠正的优先级高于旧模型推断，但不把用户自设伪装为原作 Canon。

### 3.2 检索与表达

当前轮先固定用户×角色实例、活动包、来源修订和撤销代次，再过滤无权、过期、超剧情截止点或 disputed 的条目。普通问答优先精确过滤、关键词/全文检索和时间排序；角色原作问题检索 Character Wiki/Canon，近期生活问题检索 Companion Timeline/User Wiki，表达方式使用 Soul/Relationship。跨域相同事实按稳定来源与事实引用去重；结果控制在既有 Context 总预算内，未命中就不补造记忆。

语义向量或图检索仅在固定样本证明必要且可维护时再评估，不作为 0.85 交付门槛。回复不必逐句播报出处，但管理视图应可定位本轮使用了哪些条目、哪些被排除以及原因；默认诊断只记 ID、状态、版本和预算，不持久复制私人正文。

### 3.3 用户控制与隐私

候选默认不等于已确认的长期事实。来源不可用、Observation 未经长期保存授权、配对不符或角色包未激活时，编纂应停在不可用/待处理状态。用户能看到“系统记住了什么、依据是什么、何时适用”，并对单条候选或现行条目作纠正/遗忘。界面复用已有 0.7/0.8 管理入口与逐页参考审核规则，具体布局留待界面实施时确认。

遗忘要贯穿候选、Wiki/Soul/关系派生项、关联索引、Context 缓存和页面投影；保留最小无正文 tombstone 以阻止后台重建。角色切换、资料撤销或授权变更应使在途编纂与迟到检索失效。原始 History 的删除范围与其他存储的撤销范围分别显示，不能因页面消失就声称所有副本已清除。

## 4. 依赖、剪枝与发布边界

| 前置能力 | 使用条件 |
| --- | --- |
| 0.7 / 0.79 连续性 | 正式消息写读、来源验证、配对隔离与派生遗忘达到对应准入门槛；模块级 AUTO_PASS 不代替生产接线 |
| 0.8 Event / Observation | 只有实际交付的事件类型可进入候选；临时画面默认不沉淀，保存须有明确授权和可撤销来源 |
| 0.65 宿主 / Context | 使用现有包、Memory 生命周期、单一轮次与 Context 扩展；没有第二条后台维护或 Dialogue Pipeline |

本版剪掉：全网自动爬取、批量编纂海量论文/小说、通用个人知识管理器、自动补全无来源角色设定、复杂 ontology/GraphRAG/Neo4j、所有内容统一向量化、跨角色默认共享私人资料、每轮全量重写 Wiki、自动改变原作 Soul。已有 0.7 的来源/链接/supersedes 能力只核对和补齐真实质量缺口，不以新名字重新实现一遍。

0.85 首发范围为**已授权资料与真实对话形成的少量高价值条目**，至少覆盖用户目标、近期重要经历、稳定互动偏好及角色原作事实各一类。观察类内容只有在 0.8 保存契约通过后纳入；Work 回执和知识库文章保持各自数据域。若上游未交付，相关能力保持关闭，不能用假来源宣称整版完成。

| AC | 自动证据 | 真实/人工证据 |
