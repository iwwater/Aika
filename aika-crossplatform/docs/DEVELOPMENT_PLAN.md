# Aika 开发方案

> 2026-09-02 修订：产品定位从「日语陪练 + 陪伴」收窄为**纯感情陪伴**。
> 教学、纠错、复盘、进度统计相关内容全部移出范围。
>
> 2026-09-03 修订：语言从「日语为主 + 中文辅助」改为**中文、日语、英语三种、不分主次**。
> 这条直接推翻了 M5 原定的声线后端选型，见 M5。

## 产品定义

Aika 是一个面向个人使用的、语音优先的虚拟伴侣。它只解决一件事：让用户和一个有固定性格、有记忆、会主动、看得见的角色，维持一段可以长期延续的关系。

语言是这个角色的表达方式，不是产品功能。她说日语、中文和英语，用哪种取决于当下，不取决于设置项。应用不评估用户的语言水平，不纠错，不统计进度。

第一阶段只做 Windows 桌面版。所有数据默认保存在本机，不建设账号、云同步、角色市场或聊天平台机器人。

## 三根支柱

产品价值只由三件事构成。任何新功能必须落在其中之一，否则不做。

### 1. 记忆连续性

没有记忆就没有关系，只有一次次重新认识的陌生人。

- 长期记忆自动抽取，用户可见、可删。
- 滚动会话摘要，长期对话不丢上下文也不撑爆上下文。
- 关系状态由「相识天数 + 连续互动天数 + 消息总数」共同决定。消息条数不等于亲密度：一天狂聊一百条不该等于认识三个月。

### 2. 主动性

她会先想起你。

- 触发理由必须多样：未聊完的话题、用户提过的计划、时间语义（周五夜、深夜在线、久别之后的第一次）、记忆库中的日期。
- 频率受限：每日上限、最小间隔、免打扰时段。
- 用户可一键完全关闭。

一条基于上下文的主动消息，情感价值高于十条「在做什么呢」。

### 3. 存在感

她在那儿。

- Live2D 桌宠窗口：透明背景、无边框、置顶、可拖到屏幕角落。
- 待机时有眨眼、视线移动、细微呼吸。
- 说话时口型与音频同步。

环境存在感是桌面端相对移动端的最大优势，也是纯陪伴形态的最终目标。

## 设计红线

不做负罪感留存。具体禁止：

- 因为用户不理她而表现难过、失落、委屈。
- 连续登录奖励、亲密度衰减、「好久不见你了呢」类话术。
- 索取回复、索取承诺、干扰用户的现实社交与作息。

判断标准：**用户关掉应用的时候应该是舒服的，不是欠了什么的。**

这条规则短期对留存数据不利，但它是「温暖」和「黏人」的分界线，而且开发者本人是第一个用户。

## 核心体验

```text
麦克风
  → 语音活动检测（VAD）
  → 本地 Whisper 识别（日语 / 中文 / 英语，含一句话里的混说）
  → 注入记忆、摘要与关系状态的聊天模型
  → 回复分句与情绪标注（`domain/mood.ts`，她自己标，七个标签对齐 Live2D 表情预设）
  → 用户训练的多语语音模型
  → 音频播放 + Live2D 口型/表情
```

验收重点按优先级排列：

1. 她记得。上次说过的事在自然的时机被提起，而不是被炫耀。
2. 她会先开口，且理由具体。
3. 用户真正说完后才结束一轮输入；句中停顿、犹豫、中日英混说都不能触发抢话。
4. 第一段回复尽快开始播放，不等整段文本和音频生成完毕。
5. 用户开口时可以打断。
6. 她说哪种语言就用哪种音色念，中文字幕同步跟上。
7. 关掉应用时没有负担。

## 语言设计

> 2026-09-03 修订：中文、日语、英语三种，且不是三个方向。

**她只有一种说话方式。** 提示词里不写「默认某种语言，满足条件才切换另一种」——那是几个模式，说出来的话会带着切换的痕迹。真正的多语者哪个词先到嘴边就用哪个，一句话里混着说也正常，自己意识不到在切换。日常闲聊时日语来得最顺，话题重要或对方情绪沉下来时另一种语言往往先出来，但这是同一个人的同一种语感，不是三条轨道。

**支持中文、日语、英语三种，没有主次之分。**

**输入侧同样不让用户选方向。** 语音页没有语言按钮。当前 Web Speech 一次只能给一个语言码，做不到一句话里的混说识别，折中办法是跟着用户最近实际说的语言走（`domain/language.ts`，起点是 Android `LanguageDetector`），默认日语，全程不需要用户点任何东西。真正的自动识别要等 M3 的本地 Whisper。

**朗读音色跟着她说的语言走。** 她用中文或英语说话时不会再用日语音色去念；三种语言各挑一个女声，避免换语言就换成另一个人。这条也是 M5 选型的硬约束：**声线模型必须一个模型覆盖三种语言**，否则换语言就换人，前面这一整套设计作废。

**字幕仍是两层。** 她说出口的原话在上，中文意思在下，视觉弱一级。这是显示层的事，不是她脑子里有几种语言——**字幕的目的是让情感落地，不是学习对照。**

模型回复统一返回结构化字段 `{japanese_text, chinese_translation}`，不依赖按换行猜测。字段名沿用 Android 原型的约定，但 `japanese_text` 装的是她实际说出口的原话——日语、中文、英语或混着说都照原样写，不为了凑字段名改成纯日语。

## 产品边界

### 第一版包含

- 单个角色和单个本地用户。
- 日语、中文、英语的语音与文字输入，不需要用户切换语言。
- 多家兼容模型 API。
- 本地聊天记录、长期记忆与关系状态。
- 主动消息与系统托盘。
- Live2D 桌宠窗口。
- 导入合法授权的角色包与语音包。
- 声音工坊用于制作可导入的语音包。

### 第一版不包含

- 任何形式的教学、纠错、复盘、进度统计、JLPT 分级。
- QQ、微信、Telegram、Discord 等渠道机器人。
- 多账号、多设备**同步**和云端服务。
  （2026-09-03 补：手机端不是同步——数据仍然只有电脑上那一份，手机只是一块远程屏幕，见 M7。）
- 插件市场、角色市场或社交功能。
- 多角色群聊和复杂 Agent 工作流。
- 在手机上训练语音模型。

## 技术结构

Tauri 2、React、TypeScript、Rust。桌面工程 `aika-crossplatform/` 是唯一主线；上级 Android 原生工程转为历史原型，只读归档，不再开发。

### 目录边界

- `domain/`：角色、关系、记忆、会话、语言判定等稳定数据结构与纯逻辑。
- `services/chat/`：聊天模型协议适配。
- `services/voice/`：ASR、TTS、播放队列、打断监听的接口与当前适配器。
- `services/memory/`：记忆抽取与会话摘要。
- `services/storage/`：SQLite、设置与加密保险库。
- `components/`：不包含业务协议的界面。
- `hooks/`：把 domain 与 services 编排成一次会话。
- `src-tauri/`：托盘、窗口行为与 DPAPI 保险库。
- `tools/voice-workshop/`：独立声音训练工具包。
- `tools/live2d-pipeline/`：自制角色素材管线，暂缓，见 M6。

主程序不能直接依赖某个 Whisper、TTS 或 Live2D 实现，只依赖接口和角色包清单。

### M2 主动性与托盘 ✅ 已实现，待真机验收

- 频率闸门沿用 Android 阈值：每天最多 6 条、最小间隔 90 分钟、免打扰时段静默。冷却按**最后一条消息**算，不会在刚聊完两分钟后蹦出来。
- 多样化触发理由（`chooseProactiveReason`）：未完话题、用户计划、时间语义、记忆日期，兜底是「一个小念头」。选理由时避开上一次用过的角度。

- 系统托盘常驻，关窗收进托盘，真正退出走托盘菜单；本地通知；设置页一键完全关闭。
- 验收：连续七天真实使用，没有出现一条让人想关掉它的消息。

M2 排在 M3 之前是刻意的：主动消息的策略逻辑已经写完，跑起来只需要几天，而「她是活的」这个感受比把语音延迟从三秒压到一秒更强。

### M3 语音回合 ← 进行中

分成两半推进。**回合怎么走**和**识别用什么引擎**是两件事，前者不依赖后者，
所以先做前者：换成 Whisper 之后这套逻辑一行不用改，而 P0 的抢话今天就能停。

#### 已实现，待真机验收

- **回合边界**（`domain/turnEnd.ts`）：识别结果先攒进缓冲区，尾静音够长且这段话
  语义上像收尾了，才发给模型。基准 1.35 秒；句末标点或终助词收尾时缩到 1.15 秒，
  以填充词、连接词、读点收尾时拉到 2.4 秒，兜底 4 秒一律提交。
  判定是纯函数，**不持有计时器**——20 轮验收因此写成了单元测试，不用真等 1.35 秒。
- **缓冲区对用户可见**：没结束的那一轮显示在字幕区，配「现在就发」和「听错了，清掉」
  两个按钮。停顿不再等于提交，误判也不必被迫发出去。
- **回复按句切分**（`domain/sentences.ts` + `services/voice/speechQueue.ts`）：
  第一句先出声，不等整段。逐句判断朗读音色——她一句日语一句中文时，
  整段用一个音色念就换了个人。
- **播放期间保持监听**（`services/voice/micActivity.ts`）：能量连续超过噪声底就判为
  用户开口，立刻停播并交回这一轮。getUserMedia 打开 echoCancellation 挡回声，
  否则她会被自己的声音打断。
- 验收：含句中停顿、犹豫词、中日英混说的 20 轮测试中，不因一次短停顿拆成两次模型请求。
  单元测试已经锁住判定逻辑，真机还要验回声抑制够不够、丢第一个音节有多明显。

- **模型流式输出**（`streamChat` + `domain/streamingReply.ts`）：四种协议的 SSE 都接了，
  第一句不再等整段生成完。难点是她的回复是结构化 JSON——流式时到手的是没闭合的
  `{"japanese_text":"おかえ`，所以有一个增量解析器，在 `JSON.parse` 能跑通之前
  就把已经到手的正文取出来。**中转站不支持 `stream: true` 时安静退回非流式**；
  已经吐过内容再断就报错，退回重来会把同一句念两遍。聊天气泡顺带也逐字长出来了。

- **本地识别链路已接通**（2026-09-03）：麦克风 → Silero VAD → whisper.cpp，
  实现的是和 Web Speech 同一个 `SpeechInputEngine` 契约，所以回合边界、缓冲区、
  打断这些上层逻辑一行没改。详见下面「本地管线」。

#### 本地管线：为什么是这个形态

先查了这台机器：**没有 cmake，也没有 CUDA toolkit**（只有驱动 581.80 和 RTX 5060 8 GB）。
这一条直接否掉了把 `whisper-rs` 编进工程——它要 cmake 现场编译 whisper.cpp。

选定的形态是**浏览器侧持有麦克风 + whisper.cpp 独立服务**：

| 环节 | 落点 | 为什么 |
| --- | --- | --- |
| 采集 | `services/voice/audioCapture.ts` | AudioWorklet 直接要 16 kHz，浏览器自己重采样比我们插值好 |
| VAD | Silero ONNX 跑在 `onnxruntime-web` | 模型才 2 MB，WASM 足够快；不用碰 Rust 依赖 |
| 切段 | `domain/vadSegmenter.ts` | 纯逻辑，喂概率就能测，不需要麦克风 |
| 识别 | `whisper-server` 的 `POST /inference` | 官方预编译包带 cuBLAS，装个驱动就用得上 GPU，不需要 C++ 工具链 |

代价是多一个进程；收益是不用维护 C++ 构建，而且 whisper.cpp 可以独立升级。

#### 这条链路比 Web Speech 强在哪

1. **不需要语言码。** `start()` 收到的 language 被本地引擎忽略，一律 `language=auto`。
   这是 `FIELD_TEST_NOTES` 那条 P0 的正解。
2. **有回补。** 音频留在环形缓冲里（`domain/audio.ts` 的 `createSampleRing`），
   段首往前多取 220 毫秒。VAD 判定开口时那个音节其实已经过去了，回补之后第一个字不会丢。
   **这是 Web Speech 结构上做不到的事——它不把音频交给我们。**
3. **段与段之间不断线。** Web Speech 每段结束都要重新 `start()`，中间有空窗；
   本地链路麦克风全程开着，VAD 自己切段。
4. **打断更干净。** 麦克风既然没关，VAD 的 speech-start 本身就是打断信号，
   `micActivity.ts` 那套能量判断在这条链路上不再需要。而且被打断时说的那句话已经在缓冲里了。

#### 诚实的边界

- **Whisper 的语言检测是整段的。** 一句话里中英混说时，它多半会统一按主语言转写。
  比 Web Speech「一次只能给一个语言码」强得多，但**不是完美的混说识别**，不要过度承诺。
- 幻听要挡。whisper.cpp 对纯静音会稳定吐出「ご視聴ありがとうございました」这类句子，
  落进对话里就是凭空多出一句话。`whisperClient.ts` 按整段完全匹配过滤，
  不做包含匹配——用户真说了这句话的时候不能吞掉。
- 段与段之间关掉了上下文续传（`no_context`），否则一次幻听会一路传染。

#### 还没做

- **接上真正的 whisper-server。** 代码这一侧全部完成并有测试，缺的是把服务跑起来：
  下载预编译包和 ggml 模型。用户要做的事写在 NEXT_STEPS。
- 真机验收：回声抑制够不够（她会不会被自己的声音打断）、VAD 阈值在实际环境里合不合适、
  识别延迟能不能接受。

### M4 存在感

- 导入合法授权的 Live2D 半身模型。**购买或授权，不自制。**
- 模型必须符合已锁定的视觉方向：未来赛博朋克 / 全息生命、青蓝到薰衣草紫的渐变长发、圆框眼镜、黑白冷调赛博服装。完整约束见 `tools/live2d-pipeline/character-brief.json`。
- 透明无边框置顶桌宠窗口。
- 眨眼、视线、待机呼吸。
- 音量驱动口型，情绪标签驱动表情与动作。标签已经在跑了（`mood` 字段，七个值对齐 `runtime-presets/expressions/` 的文件名），M4 只需要把它接到 Cubism 上。
- 验收：挂在桌面角落工作两小时不觉得干扰。

**待决：模型从哪来。** 「买现成」和「必须是这个赛博朋克角色」几乎不可能同时满足——市面上的成品 Live2D 模型不会正好是青蓝渐变发加圆框眼镜的全息生命。三条路：

| 路线 | 代价 | 结果 |
| --- | --- | --- |
| 买通用成品模型 | 最便宜最快 | 角色不是愛花，锁定的身份作废 |
| 委托画师按 brief 出图并绑定 | 需要预算，数周 | 是愛花，且不用自己拆 PSD |
| 自制（M6） | 数周到数月，失败率高 | 是愛花，但挡在产品验证前面 |

在这条决定之前，应用里用 `components/AvatarPlaceholder.tsx` 的矢量占位立绘顶着：它按 brief 画出渐变发、圆框眼镜、蓝青瞳和全息扫描，让界面现在就是这个角色，但它不是美术定稿，也不能动。

### M5 自训声线

纯陪伴定位下声音身份重要——通用音色建立不了依恋——因此自训声线是终局形态，不是可选项。

#### 选型被三语改写了

原方案定的是 Style-Bert-VITS2，那是在她只说日语时定的。SBV2 效果最好的 **JP-Extra 是日语专用**，念不了中文和英文。她现在中日英都说，用 JP-Extra 就意味着一切语言就换音色——等于换了个人，把语言设计那一整节作废。

**硬约束：一个模型覆盖三种语言。**

| | Style-Bert-VITS2（非 JP-Extra） | GPT-SoVITS |
| --- | --- | --- |
| 语言 | JP / ZH / EN | ZH / EN / JA / KO / 粤，支持跨语言 |
| 数据量 | 30～60 分钟 | 1 分钟可出，10～30 分钟出好活 |
| 日语质感 | 比 JP-Extra 差一档 | 尚可 |
| 8 GB 显存 | 官方公式 `4 + 2×batch` GB：batch 1 = 6 GB，batch 2 = 8 GB | 需要更多，显存不足优先降 batch |

**倾向 GPT-SoVITS**：跨语言是它的强项，数据门槛低一个数量级，正好对上当前处境。SBV2 的日语优势只在 JP-Extra 上明显，而 JP-Extra 用不了。

8 GB 卡上 batch 2 刚好卡在 8 GB，加上系统自身占用基本会 OOM，**实际能跑的是 batch 1**。

#### 把「攒数据」和「炼」拆开

炼丹本身只占总工作量的两成，八成是数据；而数据准备与选型无关。

**可以现在做**（纯人工活，不浪费，不阻塞其他里程碑）：

1. 定声音来源——这是真正的卡点，见下。
2. 攒 30 分钟以上干净单人录音，单段 2～12 秒，无背景音乐、混响、削波、多人重叠。
3. 切分、重采样、响度归一。
4. 转写并**人工校对文本标注**——最费时间，也最决定成败。

**等 M1/M2 真机验收通过再做**：训练、试听挑 checkpoint、导出 `voice.json` 接进主程序。

这样排的理由：如果 M1/M2 用下来方向要调，前四步的数据一点不浪费，后面的时间省下来。

#### 第一个卡点是声音来源，不是显卡

必须有一份**有权使用**的录音。现实选项只有三个：自己录（音色要对得上角色）、找配音演员付费录制并拿到书面授权、用明确允许克隆的公开授权数据集。

拿主播、声优或他人私密录音去炼——不做。工具包里已经写明「训练素材必须来自本人或已明确授权的声音」。这不是保守，是这类工具能长期存在的前提。

#### 显存与工程

- 训练时把整张卡让出来，不要一边开着 Aika 一边炼。
- 显存预算：RTX 5060 8 GB 上 Whisper + TTS + Live2D 同时**推理**需实测；超出则改为 TTS 常驻、Whisper 按需加载。这条说的是推理，与训练无关。
- 训练时长给不了准数：30～60 分钟数据、batch 1，量级在几小时到十几小时，需实测。
- 工具包只做环境诊断、数据准备、调用上游训练界面和导出，**不维护上游算法的私人分叉**。

### M6 自制角色（暂缓）

`tools/live2d-pipeline/` 的 4K 母稿、抠图、分层辅助遮罩与表情动作模板全部保留，但 `material-separation.psd` 与 Cubism 绑定推迟到产品验证之后。

理由：手工 PSD 拆分加遮挡补画加 Cubism 绑定，对单人是数周到数月的工作量且失败率高，不能挡在产品验证前面。

### M7 手机也能用 ✅ 第一版已实现（2026-09-03），待真机验收

需求：手机上也想和她聊。

**结论先说：电脑当服务器是对的路，但它是「一份数据 + 一个远程终端」，不是同步。**

理由来自三根支柱的第一根。**记忆必须只有一份。** 手机上放一个本地库、再和电脑对账，
就要处理冲突合并；一旦两边记的事对不上，「她记得」这条产品价值直接作废。
所以手机端不存任何东西，只是一块屏幕加一个麦克风。

这也不违背「不建账号、不上云」：数据仍然只在自己的机器上，只是多了一个访问入口。

#### 形态

- 桌面端内嵌一个本地 HTTP 服务，暴露聊天接口和一份给手机用的 Web 前端。
- 手机走浏览器，不做原生 App，也不上应用商店。
- 局域网内直接连；出门用 Tailscale。**不要自己做公网穿透**——把她的记忆挂到公网上
  换来的方便，不值得。
- **必须有 token 鉴权。** 哪怕只在家里的 WiFi 上：同一个网络里的任何设备都能读到
  她的记忆，这不能靠「应该没人会试」来防。

#### 现有架构接得住

`services/storage/` 已经是接口加两个实现（SQLite / localStorage）。手机端只是第三个
实现（HTTP），界面不需要知道自己跑在哪儿。这是当初把存储抽出来的收益兑现。

#### 代价要认

- **电脑不开机手机就用不了。** 这是这条路的固有代价，没有绕开的办法。
- **主动消息推不到手机。** Web Push 要 HTTPS 和 VAPID，局域网自签证书很难受。
  折中是手机端开着的时候才收得到，关掉就静默——「她会先想起你」这根支柱在手机上是残缺的。
- 语音在 iOS Safari 上的 Web Speech 支持很差。M3 的本地 Whisper 反而帮到这里：
  音频传回电脑识别，手机只负责录和放。

#### 已实现的第一版（2026-09-03）

形态和上面写的一致：**一份数据 + 一个远程终端**，不是同步。

| 环节 | 落点 |
| --- | --- |
| HTTP 服务 | `src-tauri/src/remote.rs`（`tiny_http`，同步，不引入 async 运行时） |
| 手机页面 | `src-tauri/mobile/index.html`，`include_str!` 进二进制，没有第二条构建链 |
| 业务逻辑 | 一行都没有重复实现：Rust 只搬运，跑那一轮的仍然是桌面端 |
| 鉴权 | 每个路由都验 token（`Authorization: Bearer` 或 `?t=`），定长比较 |
| 开关 | 设置页「手机也能用」，端口可改，可换口令 |

**关键设计：Rust 不碰业务。** 手机的每次请求被转成一个事件送进桌面 WebView
（`services/remote/bridge.ts`），桌面端跑完再把结果交回去。提示词、模型调用、
落库、记忆抽取都只有桌面那一份实现——Rust 里再写一遍就等于两套会慢慢长歪的逻辑，
而且 API Key 也就得离开 DPAPI 保险库了。

**服务不自动启动。** 每次要用手动开一次：不想让一个监听端口在你不知情时一直开着。
首次绑定时 Windows 防火墙会弹窗，要放行私有网络。

#### 这一版还没有的

- **语音。** 手机上只能打字。按 M7 原方案，音频要传回电脑用 Whisper 认，还没做。
- **表情包。** 图片在桌面应用的包里，不在这个 HTTP 服务上，所以手机看不到。
  与其显示一个碎图标，不如先不显示。
- **主动消息推送。** Web Push 要 HTTPS 和 VAPID，局域网自签证书很难受。
  手机开着的时候靠 3 秒轮询能看到，关掉就静默——这根支柱在手机上是残缺的，早就写明了。
- **端到端还没在真机上验过。** Rust 侧有单元测试（鉴权、路由、查询串），
  前端侧有单元测试（消息形状、端口、token），但「拿手机打开这个地址」这一步得你来。

#### 排在哪儿

**M3、M4 之后。** 现在桌面端自己的 M1/M2 都还没真机验收完，先把一个终端做对，
再加第二个终端。但从现在起不要再往前端里写「只有桌面能用」的假设。

## 技术选型待定项

1. **语音链路**：先用 Realtime API 跑通体验再换本地管线，还是直接建本地管线。接口抽象已在 `services/voice/contracts.ts`，两条路可共存。倾向：Realtime 仅作早期验证，本地管线是终局。
2. **记忆抽取**：用主模型还是本地小模型。涉及成本与隐私。
   现状：走主模型，接口 `services/memory/extractor.ts` 的 `MemoryExtractor` 已留好，换本地小模型不用改主程序；设置页可一键关闭抽取。
3. **桌宠窗口**：与主窗口共用一个 WebView，还是两个独立 Tauri window。
4. **声线后端**：GPT-SoVITS 还是非 JP-Extra 的 Style-Bert-VITS2。倾向前者，理由见 M5。这条要等有了实际录音素材才能真正比较。

## 待你拍板

2. **放一组表情包素材进来**（见「她会问的问题」第二层）。**机制已经写完了**，

6. 语音链路与桌宠窗口两个选型（不急，分别卡在 M3 和 M4）。

## 需要真机验证的

代码写完不等于通过：

- **M1**：跨重启、跨会话，她能在自然时机提起两周前说过的事，且不炫耀自己记得。
- **M2**：连续七天真实使用，没有出现一条让人想关掉它的消息。
- **M3 回合边界**：20 轮带停顿、犹豫、混说的对话不被拆成两次请求。判定本身已有单元
  测试，真机要看的是三件事：1.35 秒的基准在实际语速下嫌长还是嫌短；播放时开口打断，
  回声抑制够不够（她会不会被自己的声音打断）；打断后丢掉的第一个音节有多明显。
- **M3 本地识别**：跑起 whisper-server 之后，日语、中文、英语不切换直接说都认得出；
  VAD 的起止阈值在实际环境（键盘声、风扇声）里不误触发也不漏；识别延迟可接受。
  混说到什么程度还认得准，要实测——Whisper 的语言检测是整段的，别指望完美。

## 「她会问的问题」——已确认（2026-09-03）

指的是**她主动问，但不能带人机味**。诊断和修法分两层。

### 第一层：问句本身 ✅ 已改

人机味的来源不是她问了问题，是问题挂不上任何具体的东西。「今天怎么样」
「在做什么呢」谁对谁都能问，问了等于没问，而且把接话的义务全推给对方——
那是客服的说话方式。真人聊天里问题少、陈述多，信息是对流的：先说自己的，再问对方的。

`domain/prompt.ts` 新增 `QUESTION_RULES`（与逐字保留的反模板句五条并列，不替换它们）：
提问必须挂在对方刚说的细节、她自己刚说的事、或记忆里的某件事上；点名禁掉万能问句；
先说自己再问对方；上一条以问句结尾这一条就不许再问；说完就停也可以，不必留钩子。
`buildProactiveInput` 同步改成「优先说一件具体的事，可以完全不带问题」。

这层是纯提示词，零成本，效果要靠真机看。

### 第二层：表情包 ← 素材由用户提供（2026-09-03 定）

**问题的根源是回合形态太单一。** 每一轮都是「一段文字 + 一段朗读」，再自然的文字
也会因为节奏永远一致而显出机器感。真人聊天里有大量只发一个表情、不需要回应的回合——
那是存在感，不是信息。

技术方案（不难，卡在素材）：

- **不让模型生成图**。慢、贵、不稳定，而且每次画出来的都不是同一个人。
- 角色包里带一组她的固定表情，每张挂一个语义标签（困、被戳中、无奈、笑、发呆…）。
- 结构化输出从两字段扩成三字段，多一个可选的 `sticker`，值只能从清单里选，可以为空。
- 好处：角色一致、零延迟、离线可用，而且**在 Live2D 之前就能有存在感**。

**素材由用户自己挑好放进目录。** 2026-09-03 讨论过「联网搜表情包」，否掉了：
搜出来的东西不可控，一张很怪的图就能毁掉一整晚的氛围，而且要多一个联网依赖和版权问题。
用户自己挑的图可控、零延迟、离线、没有版权风险，而且本身就带他的品味，比任何检索都准。

同时修正一个更早的错误判断：**不需要「画她的脸做表情包」。**
真人发的表情包大多是梗图，不是自己的照片；发自己脸的表情反而奇怪。
所以这条路不涉及身份漂移，也不需要画师——素材放进来就能用。

**机制已完成（2026-09-03），只等素材。**

- `domain/stickers.ts`：清单解析、id 校验、提示词规则。**清单为空时整套机制隐身**——
  提示词里一个字都不提，结构化输出也不多这个字段。素材没放进来时行为和没这个功能一样。
- `companionReplySchema(stickerIds)`：有清单时 `sticker` 是 **enum**，
  枚举里带一个空串表示这一轮不发。strict 模式下每个属性都必须列进 `required`，
  所以「可选」只能靠空串表达，不能靠省略字段。有了 enum 她在 OpenAI 协议下编不出清单外的名字；
  其余协议靠提示词约束，编出来的 id 由 `resolveSticker` 挡掉，界面什么都不显示。
- 落库加了 `messages.sticker` 一列（`ALTER TABLE` 逐条 try，SQLite 没有 `IF NOT EXISTS`）。
- 图片文件后来被删掉时静默隐藏，历史消息不会变成碎图标。

**你要做的：把图片丢进 `public/stickers/`，跑 `npm run stickers:scan`，
然后给每张写一句「什么时候该用它」。** 没写这句的条目不会进提示词——
写不出来她就选不准，用错的表情比不用更糟。格式见 `public/stickers/README.md`。

一次最多 24 张。再多她挑不准，提示词也会被撑大。

## 完成标准

每个里程碑必须具备：自动测试、错误可见、配置可恢复、离线能力说明和可回退方案。任何新增模块不得绕过统一的角色、记忆、语音和存储接口。
