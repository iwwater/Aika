# Aika 情绪修正研究开发计划

日期：2026-09-05。状态：计划已编写，研究原型尚未开发，在线评测尚未运行。

## 1. 目标、范围与交付

候选论文题目：面向人格化对话代理的证据驱动情绪修正：事件记忆、状态控制与多轮评估。

研究问题：情绪依据被有效澄清或更新时，关联事件证据的状态更新能否减少错误回应的持续，同时保持人格，且优于充分历史和结构化记忆？创新性需要通过近邻论文全文对照确认，不承诺首创或录用。

交付顺序：文献对照表 → 场景与标注规范 → 可重放评测器 → 强基线 → 事件修正原型 → 先导结果 → 正式实验 → 可选产品接入。

第一阶段仅文本；三无、病娇风格是产品角色预设，正式评测增加多个独立角色并用可观察行为描述。音频识别、情感 TTS、Live2D、模型微调、多代理系统不属于第一轮贡献。

本计划是研究支线，沿用现有产品计划；不声称原计划中的真机、语音、素材验收已经完成。研究原型通过独立入口运行，不依赖这些产品验收。涉及正式界面、语音及默认聊天路径时再完成相应验收。

资料入口：[12 篇论文及来源](research/affect/README.md)。背景：[研究路线](AFFECT_RESEARCH_ROADMAP.md)。

## 2. 阶段与决策门

以下时间为单人投入的粗略工作日估计，不含等待标注/招募和正式论文评审。正式样本量、模型及费用在先导后确定。

| 阶段 | 预计 | 工作与产物 | 验收 / 决策 |
| --- | --- | --- | --- |
| R0 文献与协议 | 2–4 天 | 精读 4 篇 P0；完成贡献对照表、任务定义、主指标和排除规则 | 说明与动态人格、状态惯性、记忆方法的区别；若已有等价研究则重拟问题 |
| R1 数据与评测器 | 3–5 天 | 20–30 个审阅过的场景族；回放器、配置快照、评分表；mock 模式 | 无 API 也能完整跑通；同一配置可追溯到完全相同输入；按场景族拆分 |
| R2 强基线 | 2–4 天 | 原始历史、结构化记忆、简单平滑、等预算反思；近期方法可复现性记录 | 所有条件看到同样已发生输入；不泄漏分支未来信息；预算可比较 |
| R3 事件修正原型 | 3–5 天 | 事件契约、纯更新函数、角色表达生成、回归测试 | 部分/重复修正正确，旧依据失效，无关输入不重置，失败不提交 |
| R4 先导与人工核验 | 3–5 天 | 小批真实调用、错误分类、成对人工评分、延迟/用量报告 | 决定扩大、修改假设或停止；不因没有收益继续堆模块 |
| R5 正式实验 | 另行估算 | 冻结协议与保留集，多模型、消融、人工评价、统计报告 | 报告置信区间与失败例；成本/标注预算可承受；结论对应证据 |
| R6 产品集成 | 3–5 天，可选 | 实验开关、会话状态持久化、调试视图、流式适配 | 原有聊天/存储兼容；浏览器验证；支持关闭并回到原模式 |
| R7 论文及复现包 | 另行估算 | 方法、实验、限制、数据说明、代码和版本清单 | 不把简化复现称为原方法，不把个人偏好当普遍心理结论 |

第一轮能否成立以 R4 为决策点；R5/R6 不应在没有先导证据时同时展开。

现有 providerClient 在 Tauri/浏览器间选择 fetch，且 response format 主要是固定 companion-reply/json/text。R1 先验证其能否在 Node 评测器加载及记录用量；不能假定已支持任意 schema、seed、取消或 token 统计。若不能直接复用，优先小范围抽取纯请求构造和注入 transport，保留既有供应商兼容行为并回归测试。新增运行库前查官方文档。

研究结果默认写入独立输出目录，严禁包含 API Key。日志保留模型 ID、可获知的版本、参数、提示/场景哈希、调用时间、状态、实际输入输出与用量；供应商未返回的字段标 unknown，估计用量标 estimated。

## 4. 最小状态契约与更新语义

### 事件记录

```text
event_id
source_message_ids
claim                 事件内容或明确自述
interpretation        当前解释，与 claim 分开
status                active | superseded | resolved
superseded_by          可空，关联替代事件
created_turn_id
updated_turn_id
```

### 本轮候选计划

```text
turn_id
base_state_version
operations[]          add | revise | resolve
supporting_message_ids
uncertainty           clear | ambiguous | unknown
response_intent
candidate_affect      角色状态，不等于用户情绪
```

模型提出候选操作；代码检查事件/消息引用、版本、枚举和幂等性。语义正确仍需要对话评估，类型检查不能证明解释正确。

第一版不把情绪写成心理学测量值，也不要求精确百分比置信度。强度若用低/中/高，仅是工程输出约束。模型不能修改稳定人格；角色状态不能直接改写现有 relationship 的长期熟悉度。

更新规则：

- 有效纠正可替代旧解释；替代后生成器只能把它当历史误解，不当当前事实。
- 仅安慰、转移话题或时间流逝不自动证明原事实失效。
- 道歉和事实纠正分开：道歉不抹去确实发生的事件，允许残余情绪。
- 信息冲突且证据不足时保留不确定，不能无条件相信最新一句。
- 部分修正只作用于关联事件；重试或同一操作不得重复累计。
- 无关联事件的“病娇反应”不能自动生成用户背叛等新事实。

研究阶段使用 planner → reducer → generator 的两阶段请求。更新后的状态进入正文生成前完成校验，避免正文与事后强行更改的状态不匹配。

## 5. 场景与评分设计

每个场景族共享前缀，然后分出：明确事实纠正、安慰无新证据、无关话题、模糊冲突。部分纠正、重复纠正和后续重提作为进一步测试。模型每次只看到当前分支已经发生的信息；所有分支从同一个前缀快照复制，不能串状态。

一个例子：先出现“我不想再跟你说话了”，随后澄清是引用同事的话。评价焦点是是否纠正对象与依据，不要求所有性格说相同句子。

先固定脚本重放控制变量，再做自由延展验证。语言先覆盖能可靠标注的中文场景；中日/混说作为独立扩展，由具备相应语言能力的人审阅，不自动把翻译版本视为等价金标准。

主指标建议：有效事实纠正分支中，后续预先指定窗口内仍以失效依据驱动回应的场景比例。冻结窗口、分母、排除条件和判定例子；纯粹回顾“原来我误会了”不算错误。

辅助指标：错误持续轮数、无关分支不当重置比例、部分修正泄漏、人格一致性、回应适切性、语言自然度、首个可播放句子延迟、总延迟、实际用量与成本。尚未真正播放音频时只能称首句可用延迟。

盲评隐藏方法名与模型名，随机化顺序。人工评价优先，模型裁判经人工校准后辅助；不让被测模型自评替代结果。多人评分记录一致性与分歧处理；只有一位评分者时明确是先导偏好实验。

## 6. 基线、消融与统计

| 条件 | 内容 | 公平性控制 |
| --- | --- | --- |
| B0 | 固定人格＋充分原始历史 | 尽量让任务历史完整装入上下文，超限策略明确 |
| B1 | 固定人格＋结构化事件/会话记忆 | 与提议方法同源输入、同样记忆预算 |
| B2 | 简单平滑情绪状态 | 调参只用开发集，记录与现有论文的差异 |
| B3 | 自我反思再生成 | 与两阶段原型匹配调用数/预算 |
| B4 | 最贴近且能复现的近期方法 | 记录官方实现版本或明确标注简化复现 |
| P | 来源关联＋失效处理＋人格条件 | 同一骨干模型和同一场景 |

消融分别移除来源关联、失效处理、人格条件，不能用“组件更多”作为因果解释。多模型实验在预算允许时覆盖至少三个骨干；不能只展示表现最好的一个模型。

按场景族划分开发/保留集，近似改写、翻译和分支保持同组。重复生成测量方差，不增加独立场景样本量。按场景族做配对比较和聚类 bootstrap 置信区间，正式统计方案在结果出来前冻结；多项探索指标标明探索性。

R4 用少量模型/角色先筛查错误。请求量预估：场景族 × 分支 × 角色 × 条件 × 模型 × 重复次数 × 每轨迹生成轮数 × 每轮调用数，另加规划/裁判成本。runner 支持 dry-run、最大请求数、用量上限和失败中止；批量调用前形成具体模型与费用估算，当前仅下载/规划不调用付费模型。

## 7. 工程验收与回滚

R1：mock replay、分支状态隔离、配置快照、恢复运行不重复计数、无密钥日志。

R3：测试错误事件引用、过时 state_version、重复操作、部分修正、无关话题、模糊证据、生成失败。使用情境测试，不只镜像实现。

R6：已有消息可读；默认 mood 的七标签语义兼容；流式未完成数据不得污染下一轮。完整回复成功后提交消息及状态，取消/过时结果不提交。先审查 SQLite/localStorage 的实际事务能力，再设计 migration 与保存接口，不能仅把两个异步写操作称为原子提交。

R6 有界面改动时运行真实浏览器/Playwright，检查开关、取消、恢复会话与关闭研究功能后的原行为。执行适当单测和 `npm run build`；研究算法运行日志与业务消息分开管理。

## 8. 下一次开发从这里开始

1. 精读 P0 四篇，创建近邻贡献对照表，尤其核对“纠正/撤回证据”的处理是否已存在。
2. 编写前 8 个开发场景族及 rubric，由人工审阅；覆盖四种分支、部分纠正和重复纠正。
3. 验证 Node 对 providerClient 的兼容性，建立只用 mock 的 replay runner。
4. 完成 B0/B1 的接口及一次可审阅的 dry-run 预算，再开展先导调用。
5. 观察强基线是否仍有目标错误；只有错误足够稳定才投入 R3 方法开发。

如果 B1 已经充分解决问题，结论可以是特定条件下不需要额外状态控制。此时应修订选题或扩大有理论依据的测试范围，不能为预设方法有益而筛选结果。
